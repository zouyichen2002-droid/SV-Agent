## 0. 更正（2026-09-26）—— 第一版的读取器读不对你的 FL 2025 存的工程

M0-05 测并发时，监视程序去读 FL 2025（构建 5319）刚存的文件，**找不到速度事件**，报错退出。追查结果：

| 第一版写的 | 实际 |
|---|---|
| 「读 `.flp`：绿，13 个工程全部恰好读完」 | 那 12 个可用样本**恰好全是旧版本存的**（构建 1099–5098）。**构建 5164 以后存的工程多了一个 172 号事件**，它只带 1 个字节，读取器按规则读了 4 个，从这里开始整个文件错位 |
| 「结构检查是真依据」 | **它被骗过**：错位后把一段文字拆成一串「编号 0、值是可打印字符」的假事件，最后碰巧在文件末尾对齐，照样报「对」 |
| 「《Thief》带速度自动化，排除」 | 它是构建 5164 存的，**同样被读错位**，读取器根本没找到事件 156 |

依据：flpkit 0.8.1（MIT，2026-09-06）说明原文 *「event 172 is one byte on FL 2026, not the classic four」*，
并说这个大小随 FL 版本变；本机两个文件（构建 5164、5319）里 172 号后面的字节完全相同，按 1 字节读才能对齐。

**修正后重新核对（`flp.py` 已更新）：**

| 核对 | 结果 |
|---|---|
| 14 个文件（原来 13 个 + 你刚存的一个）结构对、没有假事件串、速度事件各恰好 1 个 | **14 / 14** |
| 读出的速度与 FL 自己报的一致 | **13 / 13**（你存的那个没导过 MIDI，读出 140 = 空模板的速度）· 《Thief》读出 150.0 = FL 报的 150.0000 |
| **加强后的结构检查会响**：用旧读法读带 172 号事件的两个文件 | 两个都判「错」（假事件串长 25）—— 第一版的检查对它们报的都是「对」 |
| **在你的 FL 2025 存的文件上写速度**（66、97.5 BPM） | FL 导出的 MIDI 66.0000 / 97.4999 ✓ · WAV 3.646 / 2.468 秒 ✓ · 注入「忘了乘 1000」被抓到 ✓ |

下文保留第一版的原始记录，**按这一节理解**。

## 2. 这改变了什么（按铁律）

- **定稿链路里「你在 FL 里按导出」这一下可以去掉了** → 出歌更快。PRD §11.6 已回写。
- **v1 的暗雷拆了。** 速度写错时 FL 照样能打开：忘了乘 1000，FL 会把速度钳到最低的 10 BPM，
  文件没坏、结果全错。现在知道它存在哪、怎么验。
- **「让 FL 当裁判」这个方法以后可以一直用。** 任何对 `.flp` 的写入，都能让 FL 自己导出 MIDI / WAV
  来核对 —— 不靠猜格式，也不用你打开 FL 看。

## 3. 命令行导出

### 依据（PRD §14 要求记下公开接口的依据）

**官方手册**「Exporting Audio & MIDI」页的「Command line export options」一节
（[原文](https://www.image-line.com/fl-studio-learning/fl-studio-online-manual/html/fformats_save_export.htm)）：

| 参数 | 手册原文（节选） |
|---|---|
| `/R[文件名]` | *Render project.flp to an audio file.* 可选文件名是输出文件名 |
| `/E<格式>` | 导出格式，逗号分隔，例 `/Emp3,ogg,wav` |
| `/O<文件夹>` | 输出文件夹 |
| `/F<文件夹>` | 导出文件夹里的所有 `.flp` |
| `/M<文件夹或文件名>` | 导出 MIDI |

**本机这个版本自带的更新说明**（`G:\FL Studio\Help\WhatsNew.htm`）里也有多条，证明这个功能一直在维护：

- 20.1（2018）：*New output folder option for command line rendering: /O*
- 20.7.3（2020）：*Allow specifying a single filename instead of a folder for command line render to MIDI*
- 2024.2：*Ignore the project's backup folder for command line rendering unless the /B option is used*

本机的离线手册只是个壳（12 个 HTML，首页是「如何安装离线手册」），所以手册原文取自官网。

### 实测

| 命令 | 结果 | 耗时 |
|---|---|---|
| `/R /Ewav /O<文件夹> empty.flp` | WAV 产出 · 16-bit / 立体声 / 44.1 kHz · 1.719 秒静音（空工程 = 1 小节 @ 140 BPM） | 6.2 秒（含启动 FL） |
| `/R /Ewav /O<文件夹> <演示曲>` | 161.46 秒的 WAV · 非静音 · 与它的 MIDI 长度（161.47 秒）只差 0.01 秒 | **34.0 秒**（比实时快 4.8 倍） |
| `/M<单个工程>` | MIDI 写在工程旁边、同名 | 模板 5–17 秒 · 演示曲 27–57 秒 |
| `/M<文件夹>` | **退出码 0，一个文件都不产出** | 3.9 秒 |

**手册与实际不符的那一条**：`/M<文件夹>` 按手册应该导出整个文件夹，实测什么都没做，**但退出码是 0**。
只看退出码就会以为成功了。所以 `fl_cli.py` 一律**检查产物在不在**，不看退出码。

另外：导出时 **FL 不改动工程文件**（工程的修改时间在导出前后不变）；每次测试前都确认 FL 没在运行。

## 4. 读 `.flp`

`.flp` **没有官方公开的格式文档**。读取器的结构规则来自社区逆向（PyFLP 等），
所以每一条都拿 FL 自己的输出去核对，不直接当真：

| 核对 | 结果 |
|---|---|
| 结构检查：事件恰好读完文件声明的长度，一个字节不多不少 | **13 / 13** |
| 文件头里的 PPQ（时间精度）= FL 导出的 MIDI 里的 PPQ | **13 / 13** |

**PPQ 因工程而异**：空模板和演示曲是 96，其余模板是 48。
以后往工程里写音符时间，必须按**这个工程**的 PPQ 换算，不能写死。

## 5. 速度

### 方法：不预设答案

1. 每个样本都让 FL 导出 MIDI，读出 **FL 认定的速度**
2. 把 `.flp` 里全部定长事件的值拿出来，找等于「速度 × 1000 / × 100 / × 10 / × 1」的
3. **每个样本里都对得上**的那个事件编号，就是速度事件

样本的速度必须各不相同，否则「对上了」可能只是巧合 —— v1 的两首歌恰好都是 66 BPM。

### 样本（全是 FL 自带工程的拷贝，只在本机，不进仓库）

| 样本 | FL 报的速度 |
|---|---|
| 空模板 · Dubstep · Trap | 140 |
| Breakbeat · EDM-House | 128 |
| Chillout | 82 |
| Drum & Bass | 175 |
| Funk · Jazz | 96 |
| Metal | 123 |
| 演示曲 *Song For You* | 174 |
| 演示曲 *Never Out* | 165 |
| ~~演示曲 *Thief*~~ | 排除：MIDI 里有 3073 种速度（60–150），带**速度自动化**，不适合当基准。**更正：它的 `.flp` 当时也被读错位了**（见第 0 节）；修正后读出 150 |

**12 个可用样本、8 种速度。结果：**

| 找法 | 每个样本里都对得上的事件编号 |
|---|---|
| 值 = 速度 × 1000 | **156** |
| 值 = 速度 × 100 / × 10 / × 1 | 无 |

### 写进去，FL 认不认 —— 两个互相独立的裁判

写入对象是空模板的**拷贝**，写出的是**新文件**，原文件不动。

| 写入 | 裁判 1：FL 导出的 MIDI | 裁判 2：FL 导出的 WAV（1 小节） |
|---|---|---|
| 66 BPM | 66.0000 ✓ | 3.646 秒，应 ≈ 3.636 ✓ |
| 97.5 BPM（带小数，验 × 1000 的精度） | 97.4999 ✓ | 2.468 秒，应 ≈ 2.462 ✓ |
| **注入缺陷**：想写 66，忘了乘 1000 | **10.0000** ✗ —— 检查判红 ✓ | —— |

裁判 2 的分量：它是 **FL 的音频引擎**在认这个速度，不只是 MIDI 导出器在认。
