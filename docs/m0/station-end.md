## 3. 失败案例

**M0 里检查器自己错了三次，三次都是第二个独立的裁判抓到的** —— 这是 M0 最值钱的一条经验。

| # | 出了什么事 | 怎么发现的 | 改了什么 |
|---|---|---|---|
| 1 | YIN 音准检查判 gm.dls「偏高 11 音分」—— **假红** | 换 FFT 基频谱线独立再测，gm.dls 其实准；偏的是 YIN（真钢琴的泛音偏高，把它往上拽） | 音准改成两级检查，并注入 3 种缺陷证明会响（M0-01 §5） |
| 2 | FL 命令行 `/M<文件夹>` **退出码 0，却一个文件都没导出** | 检查产物在不在 | 调 FL 命令行一律看产物，不看退出码（M0-03 §3） |
| 3 | `.flp` 读取器读不对 FL 构建 5164 以后存的工程，**结构检查还被骗过、报「对」** | M0-05 的监视程序读你刚存的文件时找不到速度，报错退出 | 172 号事件按 1 字节读；加「假事件串」检查；记录**更正、不覆盖**（M0-03 §0） |
| 4 | SynthV 导出脚本第 1 版读出 **0 个音** | 导出的 WAV 明明在唱；SynthV 的恢复文件里 8 个音都在 | SynthV 打开时会把音挪进音符库组 —— 改成读全部音符组（M0-04 §2、§3） |
| 5 | M0-05 的 FL 轮：导出那一刻进程列表为空，导出却成功了 —— 看起来像「FL 开着也能导出」 | 这个数据说明不了问题：最可能是你存完就关了 FL | 单独写探针，**先证明它看得见 FL**，再测：FL 开着时导出必失败（M0-05 §4.2） |
| 6 | 网易云：Codex 的浏览器工具打不开这个站 | 工具的站点安全策略拒绝，不是登录失败 | 按 PRD §14 的替代方案：平台操作你本人做，发布包附人工确认清单（M0-07） |
| 7 | **提交前的凭据钩子空了一个多月** | 09-27 装钩子时发现：本地 git 还指着 `.githooks`，目录却在 v2 清空时删了 | 从 v1 恢复并加固；真 key 在内存里、假 key 在一次性仓库里各验一遍（`scripts/scan_secrets.py` 开头的说明） |
| 8 | 扫描器漏报「粘在长串里的 key」 | 装的时候先写测试：新测试在旧扫描器上失败 | 按已知长度逐段比，25 条测试全过 |
| 9 | 我说错一句「v1 的钩子本身是 CRLF」 | 测试结果和我的说法对不上 → 改用 Python 按字节数，CR 是 0。Bash 工具吞了 `$'\r'` 的反斜杠，数出来的是**总行数** | 当场更正；以后数字节一律用 Python |

**规律**：1、3、4 是「检查器本身错了」，2、5 是「工具说成功、其实没有」，7、8、9 是我自己的疏忽。
前两类都靠**第二个独立的裁判**抓到；第三类靠「先写会失败的测试」和「数字对不上就停下来查」。

## 6. 关键流程 —— 你能讲清楚这几个，就过了纪律四

先自己想一遍再点开答案。讲不清的那一个，就是进 M1 前要补的。

<details>
<summary><b>① 快速试听</b>：从「候选生成」到「你听到声音」经过哪几步？为什么点「试听」几乎是瞬间的？为什么 A/B 两边要同一版渲染器？</summary>

候选（音符）→ Python worker 用 gm.dls 采样钢琴渲染成 WAV（0.27 秒）→ 你点「试听」时只是播放这个现成文件。
**候选一生成就预渲染**，所以点下去不用等。A/B 公平的前提是两边只差「候选本身」：
同一版渲染器、固定增益、同一份音符渲染结果逐字节相同 —— 渲染器一改，旧候选要先重渲染。
（V1 清单 R04、R05；M0-01、M0-02）
</details>

<details>
<summary><b>② 手改保护</b>：为什么我们从不改写你开着的 <code>.svp</code> / <code>.flp</code>？发现你改过之后系统怎么做？</summary>

M0-05 实测：SynthV 和 FL 都**不察觉**磁盘上的文件被改过，你一保存就用内存里的版本**整个覆盖**，不给提示。
所以一律写新文件。文件哈希变了 = 你存过盘 → 当作你的新版本导入，不覆盖。（V1 清单 R09；PRD §9）
</details>

<details>
<summary><b>③ 定稿链路里哪几处要你动手</b>？为什么这几处不能自动？</summary>

SynthV 人声导出要你点一下（官方脚本接口不能导出；位置和文件名已经预填）；
FL 自动导出之前 FL 必须关着（开着时命令行导出必失败）；
编曲暂时是你把 MIDI 拖进 FL（往 `.flp` 写音符还是灰）。（能力矩阵第 2 节）
</details>

<details>
<summary><b>④ 发布</b>：发布包里有什么？为什么音频一律 48 kHz？上传前你要对照哪份清单？</summary>

B站：封面静帧 + 音频的视频（H.264 / AAC 48 kHz）、SRT 字幕、表单文字（创作声明选「含AI生成内容」）；
网易云：WAV、LRC、封面、歌曲信息。48 kHz 是因为 B站视频的音频要 48000，网易云页面写「>44.1kHz」，
48 kHz 两边都满足。上传时对照 M0-07 §7 的 10 条「发布时人工确认项」；**上传、提交都是你本人**。
</details>

<details>
<summary><b>⑤ 花钱与凭据</b>：一次任务最多花多少、到线会怎样？key 为什么不会进仓库？为什么模型名要钉死 <code>mistral-medium-2604</code>？</summary>

每个任务 ≤ 30 万 token 且 ≤ 15 分钟、每天 ≤ 200 万；按 Medium 3.5 现价，单任务封顶约 ¥16。
到线就暂停、保留结果、报已花费用，你确认才继续。
key 只在被 git 忽略的 `.env` 里；万一写进要提交的文件，提交前的钩子会拦住（按哈希认，输出打码）。
`-latest` 这类别名会跟着官方更新指向别的模型 —— 版本记录里就看不出「这段旋律是哪个模型写的」。（PRD §17.2；V1 清单 ★2、★3）
</details>

<details>
<summary><b>⑥ 三色</b>：灰和绿有什么区别？举一个 M0 里「检查器自己错了」的例子，它是怎么被抓到的？</summary>

绿 = 有依据说它好；灰 = 还没有可判断的依据 —— **灰不是「差不多没问题」**。
例子：SynthV 导出脚本第 1 版读出 0 个音，但导出的 WAV 在唱、恢复文件里 8 个音都在 ——
两个独立的裁判对不上，追下去才发现错的是检查器（第 3 节 #4）。
</details>
