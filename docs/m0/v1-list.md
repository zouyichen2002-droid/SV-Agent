## 1. 结论先说

```
  R01–R14 没有一条被 M0 否掉。M0 改的是「怎么做」，不是「做不做」：
    R04 快速试听                  候选一生成就预渲染 → 点「试听」只是播放现成文件
    R05 A/B                       同一份音符逐字节相同 → 听出的差别只可能来自候选本身

  V1 最大的未知不在 M0 的范围里：
    R02 歌词 · R03 旋律和声节奏   生成一条都没测过 → M2 的第一个风险
```

**按铁律**（PRD §0），V1 能不能让出歌更好、更快，取决于 R03 生成的旋律你愿不愿意继续做 ——
M0 验证的全是它周围的管道。所以 M2 的第一步是一个**最小生成探针**：用 Mistral 的几个型号各试一次，你听过再往下搭。

### ★2 生成用 Mistral —— 你定

**09-27 连通检查**（[`spikes/m0-mistral/probe_access.py`](../../spikes/m0-mistral/probe_access.py)）：

- `.env` 里的 key 就是凭据扫描器登记的那把（哈希对得上），环境变量里的是同一把
- 列模型：HTTP 200，**53 个模型**，下面三个候选都在
- 最便宜的模型发 1 个 token 的请求：0.35 秒返回，用了 5 个 token
- 响应头里的限额：**每分钟 6000 次请求、400 万 token** —— 这么高，不像免费档，**按计费算**

| 候选 | 这把 key 能用的名字 | 官方文档怎么说 | 每百万 token 输入 / 输出 |
|---|---|---|---|
| Mistral Medium 3.5 | `mistral-medium-2604` | 「frontier-class」，面向 agent 和写代码 | $1.5 / $7.5（最贵） |
| Mistral Large 3 | `mistral-large-2512` | 开放权重的通用模型 | $0.5 / $1.5 |
| Mistral Small 4 | `mistral-small-2603` | 指令、推理、写代码合一 | $0.15 / $0.6 |

价格来自 Mistral 官方价格页 <https://mistral.ai/pricing/api>（09-27 查）；Medium 3.5 的价另用第三方价格页核过一次，对得上。
Magistral 这把 key 也能调，但官方文档把它列为要退役的，不考虑。

**M2 的最小生成探针拿这三个各试一次，你听过再定用哪个**（PRD §8.2：好不好听只能你判）。
key 只在被 git 忽略的 `.env` 里，**不进仓库、不进日志、不进任何提交的文件**。

### ★3 单任务预算上限 —— 你让我估了定

**定下来的数**（写进了 PRD §17.2）：

- 每个任务 **≤ 30 万 token**，且 **≤ 15 分钟**
- 每天 **≤ 200 万 token**（所有任务加起来）
- 到线就暂停：保留已有结果，报已花的 token 和钱，**你确认才继续**（PRD T12、§4.2 ③）

**怎么估的** —— 这是估算，不是实测。M2 的探针会记下每次调用的实际用量，到时按同一规则重算：

| 任务 | 调用次数 | 每次输入 | 每次输出 | 合计 |
|---|---|---|---|---|
| 一句话 → 规格（R01） | 1 | ~2k | ~1k | ~3k |
| 歌词候选 × 2（R02） | 2 | ~3k | ~2k | ~10k |
| 旋律 · 和声 · 节奏候选 × 2（R03）· **最重** | 2 + 各重试 1 次 = 4 | ~10k | ~13k | **~92k** |
| 反馈解释（R06） | 1 | ~4k | ~2k | ~6k |
| 局部重生成 × 2（R07） | 4 | ~12k | ~10k | ~88k |

- 「每次输出 ~13k」= 16 小节的音符、和弦、节奏写成结构化数据约 5k，再给模型的推理留 8k
- **规则：上限 = 最重任务的 3 倍。** 92k × 3 ≈ 28 万 → 取 **30 万**。时间同理：最重任务估计 5 分钟（两个候选并行、各重试一次）→ **15 分钟**
- 每天 200 万 ≈ 20 个最重任务。一个认真的创作日估计 100 万左右（5 轮旋律 + 5 轮局部改 + 歌词和反馈）

**折成钱**（按上面的官方价格；1 美元按 7.2 元粗算；「最多」按全部是输出算，是封顶值）：

| 型号 | 最重的一次任务 | 单任务上限最多 | 每天上限最多 |
|---|---|---|---|
| Medium 3.5（最贵） | 约 ¥3.2 | 约 ¥16 | 约 ¥108 |
| Large 3 | 约 ¥0.7 | 约 ¥3.2 | 约 ¥22 |
| Small 4 | 约 ¥0.3 | 约 ¥1.3 | 约 ¥9 |

**为什么加了每天的上限**（你只问了单任务，这一条是我加的）：这把 key 的限额很高、按计费算。
程序要是出了「一直开新任务」的 bug，单任务上限拦不住，一分钟就能烧掉几百万 token；每天的上限拦得住。
到线也只是暂停问你，不会丢东西。

**价格会变**：价格表写进配置、带上查价日期，**不写死在代码里**（PRD §13 同样的规矩）。

### ★4 每周投入时间 —— 你定：不定

有时间就做，按任务一步一步来。所以**不估 M1–M3 的日程**（PRD §15 已改），
只按依赖排先后、切成你读得完的小批次（纪律四）。

### ★5 冷启动目标 —— 你让我定

**定下来的**（写进了 PRD §8.1 ③）：试听链路冷启动 **20 次里至少 19 次 ≤ 3 秒**，超过就显示「准备中」。

- 怎么量：新开 worker 进程 → 载入 gm.dls → 渲染完标准样本（M0-01 的 16 小节）
- 依据：M0-02 实测中位 0.67 秒（5 次，658–692 ms）；3 秒留 4 倍多的余量 —— 和 ★3 同一条「留足 3 倍」的规则
- 生成用 Mistral 的接口，**没有本地模型要载入**，所以冷启动只算试听链路
- 刚开机、文件缓存全冷的情况没测过，M2 补测一次
