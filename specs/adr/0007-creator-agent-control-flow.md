# ADR-0007 — 借 coding agent 的机制，不借它的控制流；会话用树而非线性

| | |
|---|---|
| 状态 | **已接受** |
| 日期 | 2026-08-22 |
| 决策者 | 用户提出「不管 Pi 还是 Claude Code 都是 coding agent，创作者 agent 能借鉴吗」，实现方给出分析，结论被接受 |
| 影响范围 | 编排层的整体形状；**取代** `specs/line2-composition-chain.md` §4 的线性管线 |

## 背景

用户要求 SV-Agent 的结构仿照 Claude Code 与 [Pi](https://pi.dev/)，并提出一个尖锐的问题：
**两者都是 coding agent，而我们要做的是 creator agent，这能借鉴吗？**

这个问题值得当成架构决策来答，因为答错会导致整套编排是错的形状。

## Pi 的结构（2026-08-22 实查 pi.dev）

「minimal agent harness」，刻意做小以便扩展：

- 四层可定制：extensions / skills / prompt templates / themes，可打包分发
- 四种模式：interactive TUI / print-JSON / **RPC over stdin-stdout** / SDK
- context engineering：`AGENTS.md`、`SYSTEM.md`、接近上限时自动压缩、
  skills 的渐进披露、extensions 动态注入上下文
- **刻意不做**：MCP、子代理、权限弹窗、plan mode、todo、后台 bash
- 权限靠环境隔离（容器、tmux）而不是内建强制
- **会话是树状的**：「navigate to any previous point and continue from there」，
  所有分支存在一个文件里

## 决策

**借机制，不借控制流。**

### 可以照搬的（机制层）

这些与「agent 操作一个大型结构化产物」绑定，与产物是代码还是工程文件无关：

| 机制 | 在 SV-Agent 里的对应 |
|---|---|
| 工具是唯一能碰外部世界的路径 | 桥的六个工具面；SynthV 工程 ≈ codebase |
| 读后写 + 新鲜状态校验 | `contextId` / 指纹；等价于 Claude Code 要求先 Read 再 Edit |
| 一个逻辑改动 = 一条撤销边界 | 桥的一命令一撤销 |
| 技能按需加载（渐进披露） | 已装 4 个领域技能 |
| 子代理独立上下文做 fan-out | 并行生成 N 个歌词/旋律方案 |
| 记忆文件 | 偏好 + **被否决的方案** |
| RPC over stdin/stdout | 我现在驱动 SynthV 桥就是这个形状；后期接 Mistral 的天然接入点 |

### 必须换掉的（控制流层）—— 四条理由

**1. 验证器的强度差一个量级。**
代码有编译器和测试，是「是否有效」的近乎完备的判据。音乐没有。
`compose/checks.py` 那七项是**必要条件**，离充分条件很远。
ADR-0006 记的正是这件事：七项全绿而人耳判否。
**coding agent 过了测试基本就完事；creator agent 过了检查才刚开始。**

**2. 目标无法事先陈述。**
「让测试通过」是完备规格；「写一首关于宇宙无边无垠的好歌」不是。
创作者的品味是在迭代中被**发现**的，不是被指定的。
所以用户说的「门槛前期由我定，一直改到我认可为止」
**不是权宜之计，是这个领域唯一正确的架构**。

→ 后果：循环必须**便宜地重跑变体**，并且**累积被否决的东西**。
coding agent 优化「一次做对」；creator agent 该优化
「快速给 N 个选项，并记住哪些被杀掉了」。

**3. 失败无法定位。**
测试失败指向一行代码。「这段副歌不行」指向不了任何东西。
所以创作 agent 必须产出**创作者能指着说「不」的结构分解** ——
段落、乐句、单个音符。结构分解的粒度在这里比在 coding 里重要得多。

**4. 不可逆性的方向反了。**
写代码的风险是弄坏能跑的东西，所以 coding agent 保守、尽早收敛。
创作的风险是**过早收敛** —— 因为通过了检查就把一个平庸的旋律锁死。
所以 creator agent 应当**抵抗过早承诺，让备选活得更久**。

## 采用的循环形状

```
一句话
  ↓
发散：一次给 N 个方案（子代理并行，独立上下文）  ← 照搬 coding agent
  ↓
确定性过滤（七项检查，只判必要条件，不做审美）    ← 借鉴，但降级为「过滤器」而非「裁判」
  ↓
创作者剪枝（唯一的审美判据）                     ← coding agent 没有这一层
  ↓                              ↓
采纳 → 下一阶段              否决 → 否决记忆 ──┐
                                              │
        └──────── 回流到「发散」，方案更窄 ←──┘

以上全部存在一棵**树状会话**里（借自 Pi），任一岔口都能回去重来。
```

**这取代了** `line2-composition-chain.md` §4 的线性管线 A→B→C→D→E→F。
那一版把创作当成流水线，是错的形状：它假设每一步有唯一正确答案，
而创作的每一步都是「几个都行，选哪个看人」。

## 这条决策没有解决的问题

- **树状会话要不要自己实现。** Pi 已经有了，但 Pi 不做 MCP，而我们重度依赖 MCP（桥）。
  要么给 Pi 写 extension 补 MCP，要么自己实现树状会话。尚未决定。
- **N 取多少。** 发散出 3 个还是 8 个方案，取决于创作者剪枝的成本。要实测。
- **否决记忆怎么表示才有用。** 记「他否决了方案 B」几乎没用；
  要记「他为什么否决」——而那往往他自己也说不清。这是最难的一块，还没有设计。
- 确定性过滤的七项检查里，`prosody` 已在专业作品上定标（标记率 2.8%），
  其余六项**未经真实作品验证**。

## 什么证据会推翻这条决策

- 实际用起来发现创作者**不想**在每一步看 N 个方案，只想要一个然后改它 ——
  那么发散/剪枝就是过度设计，该退回「一个方案 + 快速修改」。
- 否决记忆积累了几十条之后，发现它并不能让新方案变好（因为否决理由无法结构化）——
  那么记忆子系统的这条用途不成立，应改为只记正面偏好。
- 七项检查在真实创作里频繁误杀好方案 —— 那么它连「过滤器」都不够格，
  只能降为「提示」，不参与自动淘汰。
