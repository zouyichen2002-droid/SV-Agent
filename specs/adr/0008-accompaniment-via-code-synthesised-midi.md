## 背景

主旋律已验收（161 音符 / 20 句 / 48 小节 / 七项检查 0 finding）。
下一步给它配伴奏。用户手上有 Suno 会员，也提出了 FL Studio。

## 选项

| | 做法 | 对齐保证 | 音色 | 代价 |
|---|---|---|---|---|
| A | **Suno 生成伴奏音频** | **无** —— 不遵守我们的 48 小节段落边界 | 好 | 低，但可能白做 |
| B | 本地生成模型（MusicGen / stable-audio） | 无 | 中 | **装不上**：见下 |
| C | **代码合成 MIDI + FL 配器混音** | **tick 级精确** | 取决于 FL 音源 | 中 |

**B 直接出局，不是权衡而是事实**：`audiocraft` 卡在 Cython<3.0 的构建门，
`stable-audio-tools` 缺 `pkg_resources`，两者在本机 Python 3.13 上都装不起来
（详见 `specs/environment-notes.md`）。

## 拍板：C

**理由是风险不对称**。对齐是这条链上唯一一个**会让前面四步全部作废**的失败模式：
词、旋律、检查、写入 SV 都做对了，只要伴奏和人声错半拍，成品就是废的，而且
无法靠后期补救。音色不对可以换音源，对齐不对只能重做。

A 和 B 都给不了对齐保证，因为生成模型不接受「第 17 小节必须是副歌、
第 25–26 小节必须是间奏」这种硬约束。C 的对齐是**构造出来的**，不是求来的。

### 分工的依据是实测的能力形状

> **2026-08-22 更正。** 本节原先写的是「flstudio-mcp 52 个工具里，写音符的只有两个
> 印度 raga 专用工具，所以它写不了我们的伴奏」。**这句是错的**，来源是我数
> `@tool` 装饰器而没有实际启动服务问它。stdio 起 `fl-studio-mcp` 0.3.0 实测
> **67 个工具**，其中 `fl_write_piano_roll_notes` 是**通用**写音符工具，
> 另有 `fl_export_midi`。结论不变，但理由必须换成下面真实的那个。

实测 67 个工具的分布：混音/效果/插件 26、查询 31、写音符 5、编排 4、MIDI 导出 1。

**写音符的真正限制不是"只支持 raga"，而是 note bridge 一次只能写一个 pattern**，
且要求 loopMIDI 端口 + 钢琴卷帘里预先 arm 过 `MCP_Apply`，音符走的是实时 MIDI 传输。
我们的伴奏是 5 个声部 × 48 小节 × 9 个段落，跨 pattern，走不了这条路。

**上游自己也这么说。** `fl_export_midi` 的工具说明原文：
它"绕开 note-bridge 的单 pattern 与 MCP_Apply 限制"，且"**不碰 FL**：
文件要你自己 File > Import > MIDI file 导入……FL 不会自动加载音源，
每条导入的轨都要自己指派 channel"。
也就是说，**上游给多轨编排推荐的就是 MIDI 文件这条路**，与本 ADR 的拍板一致。

所以分工的依据是：文件有 tick 保证，实时 MIDI 传输没有。
而 MCP 恰好强在我做不了的事上（音源、EQ、压缩、混响、增益结构），
它还能**读用户实际装了哪些插件和预设**，推荐基于事实而不是我猜。

    我        → 精确的 MIDI 骨架（音符、段落、力度）
    用户      → 导入 MIDI + 给每条轨挂音源   ← 只有这两件，且**无法自动化**
    MCP       → 混音（音量/声像/路由/EQ/压缩/混响/增益结构/体检/回滚）
    SynthV    → 人声

> **2026-08-23 第二处更正。** 上面原来写的是「FL / MCP → 配器与混音」。**错了。**
> **配器（挂音源）MCP 做不到，而且这不是 loopMIDI 或这个 MCP 的问题，
> 是 FL Studio 脚本 API 的硬限制。** 工具自己的说明原文：
> `fl_plugin_list` —— "We cannot load NEW plugins (FL API limit)"；
> `fl_setup_chain` —— "FL can't load plugins -- add those manually"。
> 67 个工具里也**没有任何**打开工程、导入 MIDI、新建 channel 的工具
> （`fl_export_midi` 只写文件、明说"不碰 FL"）。
>
> 所以任何 FL 的 MCP 都不可能替用户完成「导入 + 挂音源」。
> 这是**能力边界**，不是待办事项 —— 不该再当成"等 loopMIDI 就能做"来许诺。
> MCP 的价值全在音源挂好**之后**的混音层，那一层需要 loopMIDI。

这条路**不依赖 loopMIDI**：导入 MIDI 是 FL 的原生功能，配器（给 5 条轨挂音源）
现在就能做。loopMIDI 只是 MCP 与 FL 之间的传输，缺它只影响**混音**那一层。

## 证据

`scripts/verify_accompaniment.py`，六项全过：

- **回读一致**：从 `.mid` 解析出的 916 个事件与生成意图**逐事件全等**（tick、音高、力度）。
  这是「tick 不丢」的直接证据，不是推论。
- **落格**：全部起点落在 1/8 拍（60 tick）格子上，无浮点漂移。
- **tempo**：MIDI 的 tempo 字段是「每四分音符多少微秒」的整数，76 BPM 表示不出来
  （789473.68…→789474）。所以判据不是 BPM 相等，而是**全曲累积漂移 0.061ms**。
- **调内 / 和弦音**：全部在 A 自然小调内；垫/贝斯/琶音全是当前小节和弦的和弦音。
- **不与旋律撞**：垫 41–55、贝斯 36–48 在旋律（59–76）下方，琶音 77–88 在上方；
  副线 67–72 在旋律频段内，靠**与旋律零时间重叠**避让。
- **敏感度**：注入四个缺陷（偏 1 tick / 垫顶音抬回 C4 / 副线挪进主歌 / 贝斯弹非和弦音），
  四个全部被抓到。**只报 0 的检查不算检查。**

### 过程中被检查抓出来的两个真实缺陷

1. **间奏和弦错了**：原来靠「沿用前一个和弦」，于是间奏继承了副歌 1 末句的 G，
   与曲式写的 Am 不符。副歌 1 落 G 是把张力交出去，间奏解到 Am 才是那个张力的兑现。
2. **垫的顶音撞人声**：顶音 C4(60) 与主歌 2「向(60)／更(59)／深(60)」形成同音与半音，
   同时发声会打拍。改成顶音 ≤55(G3)，离旋律最低音留 4 个半音。
   低垫 + 高琶音、中间给人声留洞，本来就是这类编排的常规做法。

另有一个我自己的错误值得记下：贝斯原来在第 3 拍降八度，F 和弦上变成
MIDI 29 = F1 = 43 Hz —— 小音箱上只剩浑浊，听不见音高。改为同八度重击 + 五度下行推进。
