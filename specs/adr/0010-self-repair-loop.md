# ADR-0010 — 自修复循环：把七项检查当成可求最小值的代价函数

| | |
|---|---|
| 状态 | **已接受** |
| 日期 | 2026-08-23 |
| 决策者 | 用户选定的第二步（第一步是 [ADR-0009](0009-write-svp-directly.md) 直写 `.svp`）；生成器「先用我，流程通了再换 Mistral」 |
| 影响范围 | 新增 `toolkit/svagent/compose/repair.py`、`scripts/repair_demo.py`；`Finding` 增加 `targets` 字段 |

## 背景

用户的判断：**「看起来这个更适合做 workflow，但我想做一个真正的全自动创作助手」**。

workflow 的每一步由作者写死。agent 要自己决定下一步做什么。
我们手上有一个别处少见的东西可以支撑这件事：**可程序化的奖励信号**。
七项检查把「这段旋律有没有问题」变成一个能求最小值的数。

## 拍板

把七项检查包成代价函数，做一个受它约束的**搜索**：

    generate → check → repair → re-check，直到 0 finding 或收敛

    代价 = Σ(severity 权重 + prosody 得分)
    block=100  warn=10  info=1

### 三条设计约束

1. **回归守卫**：一次修复必须让总代价**严格下降**，否则回退。
   修 `leap` 极易顺手制造 `scale` 越界；没有守卫会左右横跳。
   「相等也拒绝」是刻意的 —— 否则会在等价解之间打转。
2. **不可修就拉黑，不重试**。`count` 直接进不可修集合：字数与音符数不符
   是结构问题，挪音高解决不了。
3. **全过程可审计**：每次尝试（接受/拒绝/原因/改了哪个音符）都进 history。

### 搜索空间刻意只含「音高 + 时长」

不增删音符、不改歌词。理由是**耦合**：增删音符会同时破坏 `count`、
打乱 `phrases` 下标、让 `prosody` 的字组对不上 —— 一次修复引发三处坍塌。
限制搜索空间之后，`count` 与 prosody 的 block 分支**永远不会被修复动作引入**。

为此给 `Finding` 加了 `targets: tuple[int, ...]`（涉及的音符下标）。
纯增量改动，`melody_v2` 回归仍是 0 finding。
**不要正则解析 `where`** —— 那是给人读的。

## 证据

`scripts/repair_demo.py`：往已验收的 `melody_v2`（0 finding）注入可复现的缺陷，
看循环能否修回来。**已知答案的测试**，比拿一首真正的坏歌强。

4 种缺陷量 × 6 个随机种子 = 24 次运行：

| 缺陷数 | 收敛 | 典型初始 findings | 典型迭代轮数 |
|---|---|---|---|
| 4 | **6/6** | 6–9 | 3–5 |
| 8 | **5/6** | 11–22 | 7–10 |
| 16 | **5/6** | 24–34 | 14–18 |
| 24 | **4/6** | 40–56 | 23–32 |

**合计 20/24 收敛到 0 finding，全程零人工干预。**
24 个缺陷 = 全曲 161 个音符里 15% 被破坏，这个量级下仍有 4/6 收敛。

### 4 个未收敛的案例全部是 `prosody`，而且是有结构的

不是随机抖动。逐例核查后确认：

    缺陷8  种子1：打坏时 prosody 2 → 残留 1，**新产生 0**
    缺陷16 种子3：打坏时 prosody 1 → 残留 1，**新产生 0**
    缺陷24 种子0：打坏时 prosody 8 → 残留 1，**新产生 0**
    缺陷24 种子3：打坏时 prosody 7 → 残留 2，**新产生 0**

**修复循环从不新产生 prosody 问题**，且每次都在减少。回归守卫是有效的。

残留的是硬骨头（「按」4 声、「到」4 声、「向」4 声），它们的真正修法是
**换词**，而换词在设计上被排除在搜索空间之外。

## 这条边界的意义

    6 项客观检查   → 修复循环全自动搞定
    1 项启发式检查 → 循环能大幅削减，但到不了 0

这不是缺陷，是**分工线**：倒字是词与旋律的关系问题，修法在**歌词层**。
而歌词层正是下一步生成器（先是我，后是 Mistral）要负责的。

所以这个结果直接定义了生成器的职责：**不是「写得好」，而是「写出让修复
循环能收敛到 0 的候选」**，其中倒字必须由它在选词时就避开，
因为下游修不了。

## 什么证据会推翻它

- ~~修复后的旋律**过了全部检查但明显更难听**。~~
  **2026-08-23 已验证一次，未触发。** 创作者听 8 缺陷档的修复产物
  （7 个音高 + 2 个时长被改，与原始版同为 0 findings），判定「听感很好」。

  **值得记下的是我预测错了。** 我事先说「预期『我忽然觉得手很沉』那句会不对劲」
  —— 理由是循环把该句中段抬高了 4–7 个半音（然 F4→B4、觉 G4→C5、
  得 F4→A4、手 E4→B4），而原版是全程下行落 C4 收沉，
  七项检查里没有任何一项能表达「这里该沉下来」。

  这个预测**被创作者的耳朵否掉了**。也就是说：在这一例上，
  「乐句情绪轮廓」这个我以为缺失的维度，**并不构成可听差异**。
  有先验偏差的是我，不是检查器。

  **范围限制**：只有一例（8 缺陷 / 种子 42 / 改动 9 个音符）。
  这条推翻条件是**被削弱，不是被关闭**。24 缺陷那档改了 13 个音符
  （含 −10、−9 半音的大幅下移），还没有人听过。
- 缺陷量继续加大时收敛率断崖式下跌（说明是局部搜索的运气，不是有效策略）。
- 出现修复循环**新产生**的 finding 且无法消除（说明回归守卫有洞）。
