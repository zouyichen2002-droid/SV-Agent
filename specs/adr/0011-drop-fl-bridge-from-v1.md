# ADR-0011 — FL 桥从第一版主链路移除

| | |
|---|---|
| 状态 | **已接受** |
| 日期 | 2026-08-23 |
| 决策者 | 创作者：「FL 桥确实没什么用，可以从第一版的逻辑中删除，如果后面有可能再加上」 |
| 影响范围 | 移除 `flbridge.py` 的所有引用；重写 `analyze_mix.py` 去掉 FL MCP 依赖；**loopMIDI 不再是前置条件** |
| 取代 | [ADR-0008](0008-accompaniment-via-code-synthesised-midi.md) 里「MCP → 混音」那部分分工 |

## 背景

ADR-0008 把 FL 桥写进了分工：「我出 MIDI，用户挂音源，MCP 做混音」。
装配完成后，那一层的价值被两件事逐步侵蚀干净。

## 为什么删

**一、混音那一层被 FL 自己的 API 卡死。** 26 个混音工具全部要求
「目标插件已加载」，而 FL 脚本 API 不允许加载插件
（`fl_plugin_list` 原文：*"We cannot load NEW plugins (FL API limit)"*）。
所以它的前置条件是一串手动操作，而手动操作正是这个项目要消除的东西。

**二、直写文件把它剩下的用途也吃掉了。** [ADR-0009](0009-write-svp-directly.md)
之后，装配、调教、混音全部改成往 `.svp` 里写：

| 原本以为要靠桥 | 实际怎么做的 |
|---|---|
| 混音 EQ / 压缩 / 混响 | 写 `.svp` 的 `mixer.fxParams`（每条轨自带一整套） |
| 读 FL 的 tempo | 用互相关验证对齐，比读 tempo 更直接（实测偏移 −1.0 ms） |
| 频段/电平分析 | `svagent.audio`，原生 numpy |
| 写伴奏音符 | 自己生成 `.mid`（上游 `fl_export_midi` 也是这么建议的） |

**三、它不稳。** 实测中途断连一次（TX 累计 2.59 MB 心跳后归零），
「更新 MIDI 脚本」救不回来，只能重启 FL。为一个已经没有独占用途的
组件付这个不稳定性，不值。

## 删掉之后损失了什么

**只有一件：读 FL 的实时状态**（tempo / 通道 / 混音器）。

而这件事有更好的替代：
- tempo 由 `verify_alignment` 的互相关间接验证（tempo 错必然表现为漂移）
- 通道与配器情况创作者一眼就能看到，问他比问桥快

## 收益

- **loopMIDI 不再是前置条件。** 少一个内核级驱动依赖
- **不需要 FL 开着**。整条链变成纯文件操作
- `analyze_mix.py` 不再依赖那个隔离的 conda env + 48MB 第三方仓库
- 少一个会莫名断连的运行时依赖

## 顺带修掉的一个隐患

重写 `analyze_mix.py` 时把频段分析抽成 `svagent.audio`，
`step5_assemble.py` 改用同一个模块。

原来两个入口各自实现同一段 STFT —— 这正是对齐验证那次的 bug 模式：
`eval/line_offset.py` 和 `make_listening_checks.py` 各自组装管线，
一个漏了参数，产出 0.340 和 0.360 两个不同的数字，**两边都不报错**。
一个分析一个实现，是这条链的硬规则。

## 代码没有删除

`toolkit/svagent/flbridge.py` 保留，头部标注「不在第一版主链路里」。
创作者的原话是「如果后面有可能再加上」。

**同时记下一条方法论**（创作者 2026-08-23 提出）：
过早裁剪架构，是在赌「我知道将来不需要什么」。这个项目里赌错过三次 ——
FL 桥、参考垫、6 版交付。**保留可选项很便宜，重新发现需求很贵。**
所以是「移出主链路」，不是「删掉」。

## 什么证据会推翻它

- FL 放开插件加载（或出现能加载插件的第三方脚本 API）
- 需要「读创作者在 FL 里手改了什么」并据此决策
- 混音要做到必须实时试听参数的程度（离线写 `.svp` 只能一次性给值）
