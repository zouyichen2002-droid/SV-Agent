# ADR-0013 — 直写 `.flp`：配器不再由创作者逐条手挂

| | |
|---|---|
| 状态 | **已接受** |
| 日期 | 2026-09-05 |
| 决策者 | 创作者：「我需要不自己手动配器」；实测三版配器后确认「确实有区别」 |
| 影响范围 | 新增 `toolkit/svagent/flp.py`、动作 `build_flp` / `reorchestrate`、钩子 `flp`；`SongProject.acc_flp` 进 `sources` |
| 关联 | 与 [ADR-0009](0009-write-svp-directly.md) 同源：**直写文件，不走桥** |

## 背景

工作流六步里，第 ④ 步（伴奏）一直是唯一必须创作者动手的一段，
理由记在事实 **F04**：FL 的脚本 API 不能加载插件，所以「挂音源」谁也替不了。

代价不只是那十分钟。真正的代价是**伴奏在第 ④ 步之后就冻住了**：
旋律、调教、混音 agent 都能反复试，唯独伴奏一改就要走一整轮人工。
于是诊断层连「这段伴奏太满」都测不出来 —— 它手上没有能重新渲染的伴奏。

## 决定

**把伴奏 MIDI 直接拼进一份已经配好音源的 `.flp`，插件状态块原样搬运。**

关键在于：`.flp` 里插件的状态是**不透明的二进制块**（事件 213，
实测最大一块 28494 字节，那是 FPC 连采样引用）。
要保住创作者挂好的音源，**不需要看懂那块，只需要别碰它**。

所以整个模块只做一件事：把文件切成 `(事件 id, 载荷)` 序列，
改想改的那一条，其余原样拼回去。与 `agent/segments.py` 同源 ——
区域外的元素传同一个对象，不复制、不重建。

## 为什么不用 PyFLP

试过 2.2.1，**在创作者的真工程上不安全**：

| 验的什么 | 结果 |
|---|---|
| 能不能 import | Python 3.11+ 上要打补丁（`EventEnum` 空基类，`_missing_` 轮不到跑） |
| `test2.flp` 读回写 | **丢 16 字节**（播放列表事件 80 字节，它只认 32/60） |
| `Project_test1.flp` 读回写 | 长度不变但**哈希变了** |
| 读通道 | `Project_test1.flp` 上**直接 IndexError** |
| 读 BPM | 两个文件都返回 `None` |

自己写的事件级读写在同样两个文件上**逐字节往返一致**。
60 行胜过一个装不进来的库 —— 而且这条是可测的判据，不是感觉。

## 事件 id 是实测认出来的，不是抄表

- **224 = 音符**：这块 16512 字节，而 PyFLP 独立数出 688 个音符，
  16512 ÷ 688 = 24；首音解出 `pos=0 rack=2 key=86`，
  与 PyFLP 报的「D7，通道 2」吻合。**两个独立实现对上了才算读懂。**
- **201 = 插件名 / 203 = 音色名**：解 UTF-16 出来正是 `FLEX` 与 `Harmo Pad`
- **213 = 插件状态**：最大的那些块，不解释，只搬运

音符 24 字节里只有四个字段被交叉验证过（位置 / 通道 / 时值 / 音高）。
**其余字节一律从样板音符原样沿用** —— 与其猜那些位是什么，
不如抄一份确定能用的。这一点写在 `flp.py` 的注释里，不许后来者当成已知。

## 验收：创作者在真 FL 里跑过

拿《晓风残月》的工程当模板、《风筝线》的伴奏当音符，拼出一份工程：

- FL 25.2.5.5319 打开**无报错**，内存占用 405 MB（空工程不会吃这么多）
- 通道机架五条，名字一字不差：`Harmo Pad` `Acoustic Bass 1` `Crystal` `Choir Aahs` `FPC`
- 688 个音符，通道分布 `144 / 104 / 76 / 4 / 360`
- 播放正常出声

随后做了单一变量的换配器实验（音高时值力度逐字节保持，只改「哪条通道来演」），
创作者听后确认**「确实有区别」**。

## 这一条**不**推翻 ADR-0011

ADR-0011 否掉的是「MCP ↔ 活着的 FL」那条路，理由是**混音工具全都要求插件已加载**
且桥会断连。那些理由今天仍然成立，这份 ADR 走的是完全不同的一条路：
**离线操作文件，FL 甚至不需要开着。**

真正被修正的是**建造过程中先下的一个结论**：
「直写 `.flp` 已验证不可行」。那句话的证据只证明了 **PyFLP 不行**，
却被推成了整条路不行 —— 推过头了。

同一天里这类错误犯了三次（另两次：「仓库是公开的」实际是 private；
「你的改动一个字节都没丢」依据是点数而非值）。共同点是
**把没验证的假设当事实陈述**。所以本 ADR 里每个数字都注明了来源，
`flp.py` 的注释也明确区分了「交叉验证过的字段」与「原样沿用的字节」。

## 还剩什么

| 缺口 | 现状 |
|---|---|
| tempo 事件位置 | **没找到。** 两首歌都是 66 BPM，所以还没暴露；换速度的歌会用错 tempo |
| 播放列表（事件 225） | 没动。新歌小节数不同的话，pattern 摆放可能不对 |
| 新音色 | 只能在模板已有的音色间重排。要新音色得从别的 `.flp` 搬状态块（FL 自带 17 个 Demo 工程是现成的来源） |
| 渲染出 wav | **仍要创作者按导出。** FL 有没有命令行渲染，至今没确认 |
| 加第六条通道 | 仍要创作者手挂一次 —— 但那是「一次」，不是「每首歌一次」 |

所以第 ④ 步是**从三步缩到两步**（拼工程、出配器变体归了 agent；
听选与导出仍是创作者），不是清零。

## 顺带抓到的一个 bug

第一版把产物路径漏在了 `SongProject.sources` 外面。后果是
`build_flp` 写出了 105879 字节的文件、动作报 `ok=True`，
**但钩子一个没跑、没入账、没有回退点** —— 又一个不报错的错误。
唯一的破绽是钩子列表是空的。已加回归测试 `test_产物在sources里`。

## 什么证据会推翻它

- FL 换文件格式，事件框架变了（往返判据会当场炸，这是好事）
- 需要生成模板里没有的音源 —— 那时要么搬状态块，要么回到手挂
- 出现一个能安全读写 FL 25+ `.flp` 的成熟库，那时应该换掉自己这份
