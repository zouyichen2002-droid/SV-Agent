## 0. 一个决定一切的事实

**创作 agent 不能自己闭环。** 代码有测试，音乐只有耳朵。

本项目两次证明量化门槛与人耳不一致：翻唱线八项全绿而创作者判否（ADR-0006）；
修复产物我预测难听而他说没问题（ADR-0010）。

所以第一版**不是**「自动生成歌曲」，而是：

> **一个能被自然语言驱动、每一步可度量、每一步可回滚的创作助手。**

推出三条贯穿约束：

1. 循环的终止条件是「交回创作者」，不是「达成目标」
2. 度量的职责是「证明没变坏」，不是「证明变好了」
3. 人在循环内部，不只在两端

## 1. 逐个原语的映射

这是本文的核心。左列是 coding agent 的原语，右列是它在创作 agent 里对应什么。
**标 ★ 的四条是借鉴带来的实质改进**，不是换个说法。

| coding agent 原语 | 创作 agent 的对应 | 决定 |
|---|---|---|
| **工具注册表 + JSON schema** | 动作池：10 个动作各带 schema | 采用。**模型永不直接碰文件**，只经工具 —— 于是备份/原子性/校验自动生效 |
| ★ **CLAUDE.md 的层级** | 偏好分两层：`memory/preferences.md`（跨歌）+ `songs/<slug>/notes.md`（这首歌） | 采用。「这首歌要暗一点」不该污染全局偏好 |
| **Skills 渐进披露** | 已有 lyric-writing / synthv-tuning / composition-arrangement | 采用。按曲风可加新技能（古风 / 电子），这是扩展点 |
| **子 agent（独立上下文 + 工具子集 + 回报告）** | 候选生成器：生成 N 条旋律，**只回冠军 + 度量** | 采用。6 候选 × 176 音符会灌满上下文 |
| ★ **Hooks（拦截工具调用）** | 写后钩子：自动跑相关检查，失败就作为反馈回灌 | 采用。回归守卫变成**自动的**，不必每个动作自己记得 |
| **权限模式** | 声明式允许清单，**不做交互弹窗** | 采用 Pi 的取向：`tune`/`mix`/`gen_*` 自动；碰音频文件或推 GitHub 要确认 |
| ★ **上下文压缩** | **日志是记忆，上下文是工作集** | 采用，但**由窗口压力触发、不由成本触发**（见 1.8 ④）。token 不稀缺，不为省钱丢上下文 |
| **会话 fork / Pi 的树状会话** | 日志**只追加 + 带父指针** + HEAD + checkpoint | **第一版就做完整的树**（创作者拍板）。见 6.5 |
| **斜杠命令** | `/新歌` `/推进` `/状态` `/重写副歌` `/回滚` | 采用。很便宜，且决定了可用性 |
| **Plan mode（先提案再执行）** | 修改轮开始前先提案：诊断 + 打算做什么 + 预计改动量 | 采用。这正是 HANDOFF §0 的「选项 + 取舍 → 你拍板」的形式化 |
| **Todo list** | 一轮里动作多时跟踪 | 保留（创作者要求不裁剪） |
| **MCP** | SynthV 桥 | 保留但**不在主链路**（ADR-0011） |
| **Deferred tools / ToolSearch** | 10 个动作用不上 | 不做。动作数超过约 20 再说 |
| **memory 目录 + MEMORY.md 索引** | `memory/` 五层 + 索引每次会话加载 | 直接照搬。本项目已在用这个模式 |
| ★ **文件状态跟踪（Read 后才能 Edit）** | 写 `.svp` 前校验它的哈希与上次读到的一致 | 采用。**直接防住我们已经踩过的那类 bug** |
| ★ **Pi 的四种前端（TUI / JSON / RPC / SDK）** | agent 做成**库 + 薄 CLI** | 采用。这才让「先用我、后换 Mistral」在架构上干净 |
| **Pi 的环境隔离权限** | 可写路径白名单：只写 `songs/<slug>/` 与项目的 svp/mid | 采用 |

### 四处实质改进，逐条说清

**① 偏好分层。** 原设计是一个扁平的 `preferences.md`。借鉴 CLAUDE.md 的层级后
拆成跨歌的和这首歌的 —— 否则「《晓风残月》要暗」会被当成他对所有歌的要求。
**层级即作用域**，这是 coding agent 里已经解决过的问题。

**② 写后钩子。** 原设计里「回归守卫」是循环的一个步骤，意味着每个动作都要
记得调用它。改成钩子之后它是**基础设施**：任何写操作之后自动跑检查，
失败就把 finding 当成反馈回灌。漏不掉。

**③ 上下文压缩的规则变清晰了。** coding agent 靠总结压缩；我们有
**只追加的日志**，所以规则是「进了日志的就可以从上下文丢掉」。
`journal.jsonl` 是记忆，上下文只是工作集。这条让长会话不会退化。

**④ 文件状态跟踪。** 这一条最有价值，因为它**防的是我们已经踩过的 bug**：
创作者在 SynthV 里开着工程，我写盘，他一保存就把我的写覆盖掉（差点发生）。
Claude Code 的做法是「文件变了就警告、必须重读」。照搬：
**写 `.svp` 前比对哈希，不一致就拒绝并重读**，而不是靠「请先关掉 SynthV」这种约定。

**⑤ agent 做成库。** Pi 的四前端设计解决了一个我原来含糊的问题：
「先用我当 orchestrator，流程通了再换 Mistral」在架构上怎么表达？
答案是 **orchestrator 是前端**。核心是 `svagent.agent` 这个库，
前端可以是 Claude Code（现在）、Mistral（以后）、TUI、或 RPC。
换发动机不动核心。

## 1.5 外部项目的借鉴（2026-08-23 实查）

### DAWZY —— 最接近的对照项目

[arXiv 2512.03289](https://arxiv.org/abs/2512.03289)。开源，自然语言驱动 REAPER。

**它独立验证了我们两个决定**，这比我自己论证更有说服力：

| DAWZY 的做法 | 我们的对应 |
|---|---|
| "maintains grounding by **refreshing state before mutation**" | 状态从文件现算 + 写前校验哈希 |
| "**atomic scripts and undo**" | 原子写 + 写前备份 + `revert` |

**它和我们的关键分歧：动作从哪来。**

DAWZY 用 **LLM 生成代码**（现场写 REAPER 脚本），我们用**固定动作池**。

取舍是清楚的：生成代码有无限灵活性，但**生成的代码无法被八项检查约束** ——
它可以做任何事，包括悄悄破坏音乐正确性。而我们整个价值主张就是
「每一步可度量、可回滚」。所以**固定动作池对我们是对的**。

但它指出了一个真实的长尾问题：「把第 3 轨的声像左移 20%」这种动作我没有。
所以采用一个**窄逃生口**（见第 5 节）。

**它的评估维度值得抄**：Usability / **Control** / Learning / Collaboration / Enjoyment。
我的验收判据全是技术性的，**漏了「创作者是否感到掌控」** —— 而那才是决定
他会不会继续用的东西。补进第 12 节。

### PRELUDE / CIPHER —— 正好补上最弱的一环

[arXiv 2404.15269](https://arxiv.org/abs/2404.15269)，NeurIPS 2024。

**核心洞见：从「用户的编辑」里学偏好，而不是从「接受/否决」标签。**

这直接解决我标记的冷启动问题。我原来的判断是「2 首接受、1 次否决，
推不出结论，所以 ④b 第一版留空」。但**创作者一直在直接编辑 `lyrics.txt`** ——
每一次编辑都是信号，而且比二选一丰富得多（改了哪个字、往哪个方向改）。

两条具体设计：

1. **学到的偏好用自然语言表示，不是特征向量。**
   原文的理由：*"improves interpretability, allowing the user to view and modify
   the learned preference"*。这正好**化解了我设计里的一处张力** ——
   我规定 agent 绝不能写 ④a（显式偏好）。PRELUDE 的答案是：
   agent 写进**另一个文件**，自然语言，创作者随时可以看见并改掉。
   于是它是 ④b，但可读可纠正。
2. **CIPHER 按上下文检索最近的 k 条偏好**，不是用一个全局偏好。
   对我们：古风题材的偏好 ≠ 电子题材的偏好。**偏好要按题材/曲风检索。**

**诚实的限制**：该论文用 **GPT-4 模拟用户**做评估，真实用户上的效果未验证；
也没有给出「多少次编辑之后才有用」的下界。所以这是**值得试的方向，不是已验证的方法**。

### 判断不借的两样

**知识图谱式记忆框架**（Cognee / Mem0 / Letta / Zep / Graphiti）——
**规模不匹配。** 我们的记忆是 5 个小文件；引入图数据库要加一个依赖 + 一个服务，
在这个规模上没有收益。

但它们收敛出的**分类法**值得当自查表：working / episodic / semantic。
对照我们：working = 上下文，episodic = 创作日志，semantic = 预设 + 环境事实。
**没有缺类。**

**重新审视的门槛**：如果到了几百首歌、需要「找出我用过那个贝斯律动的那首」，
那时才需要真正的索引。

**七层 agent 栈**（orchestration / memory / tool interface / browser / coding /
evals / inference）—— 自查：我们有 orchestration、memory、tool interface、
evals、inference，不需要 browser 和 coding。**没有缺层。**

## 1.8 成本取向：质量优先，token 不是约束

创作者 2026-08-23 明确：**Mistral 有 10 亿免费额度，第一版尽量保证质量而非
token 成本。**

这条推翻了我几处带着「省 token」隐含偏见的设计。**真正稀缺的资源不是 token：**

| 资源 | 稀缺吗 | 后果 |
|---|---|---|
| token | **不稀缺**（10 亿） | 内部搜索、多次生成、自我批评，尽管用 |
| **创作者的注意力** | **最稀缺** | 给他看的候选数**不变**（词 2 / 旋律 6） |
| **墙钟时间** | 稀缺 | 他在等。所以并行，而不是串行地多跑 |
| **API 请求次数** | **最稀缺（实测 4 次/分钟）** | 见 §4.5。这是第一版真正的瓶颈 |

### 核心原则

> **token 花在内部搜索与自我校验上，不花在增加创作者的选择负担上。**

「省 token」和「省他的注意力」是两件不同的事，我之前混在一起了。

### 因此修正的五处

**① 诊断从「排序后试第一个」改成「并行全试」。**
原设计：模型给 3 个假设排序 → 试最优的 → 不行再试下一个（串行）。
改成：**3 个假设各派一个子 agent 并行执行 + 度量 → 取实测最好的**。
这才是子 agent 的正当用途，而且**用实测取代了模型的猜测** ——
排序是猜，并行试是测。质量严格更好，代价只是 token 和一点墙钟。

**② 内部候选池放大，给他看的数量不变。**
歌词现在是我手写 2 版。改成：**内部生成 20 版 → 八项检查过滤 →
按方向聚类 → 挑差异最大的 2 版给他**。
旋律已经是内部 72 个候选挑 1，那个做法本来就对，现在有了正式理由。

**③ 加自我批评轮次。** 生成之后先自己按对应技能的自查表过一遍
（作词技能那 10 条自检、调教的音域约束），改完再交。
这是纯 token 换质量，之前没做是因为下意识在省。

**④ 上下文压缩的规则要改。** 我原来写「进了 journal 的历史可以从上下文丢掉」——
那是省 token 的思路。改成：**保留完整上下文直到接近模型窗口上限**，
压缩由**窗口压力**触发，不由成本触发。journal 依然是持久记忆，
但不再是「丢弃上下文的借口」。

**⑤ 用最大的模型。** 不为省钱降级到小模型。

### 不受影响的两处（理由是认知的，不是经济的）

- **`auto_rounds_before_handback = 1`** —— 理由是「变好只有耳朵能判」，
  多跑一轮是在**没有奖励信号**的方向上多走一步。这与 token 无关。
- **给他看 词 2 / 旋律 6** —— 理由是他的剪枝成本（逐行读 vs 听 30 秒）。
  与 token 无关。

### 2026-08-23 实测后的修正：稀缺的不是 token，是**往返次数**

接上 API 之后测出 **每分钟只有 4 次请求**（token 却有 25 万/分钟）。
所以本节的结论要收窄半句：

> token 不是约束 —— 这条成立。
> 但「token 便宜所以多跑几次」**不成立**，因为每跑一次都要花掉 1/4 的分钟配额。
> 正确的形态是：**次数少、每次塞满**。

详见 §4.5。受影响的参数已在 §8 就地改掉。

## 2. 两种模式，不是一种

创作者指出先前的架构图「更像 workflow」。正确答案不是用循环取代顺序，
而是**两种模式并存**——这对应 coding agent 里「按计划执行」与「响应反馈」两种状态。

| | 模式 A　推进 | 模式 B　修改 |
|---|---|---|
| 触发 | `/推进`、「下一步」 | 「副歌太平」「太像上一首」 |
| 控制流 | 状态驱动，顺序 | 意图驱动，循环 |
| 为什么 | 依赖是真实的：没有音符无法调教 | 改动要归因，一次只改一处 |
| 终止 | 六步走完 | 交回创作者（默认 1 轮） |
| 现状 | **基本齐全** | **几乎为零** |

两种模式**共用同一个动作池、同一套度量、同一套钩子**。
区别只在谁决定下一个动作：模式 A 由依赖决定，模式 B 由诊断决定。

> **2026-08-23 更正。** 先前我把模式 B 画成一个独立的循环，
> 把模式 A 画成单向流程。**架构上不是这样。**
> 只有**一个** tool-calling 循环，模式 A / B 是它的**两种策略**（见 2.5）。
> 差别在模型这一轮拿什么当依据（状态 vs 诊断），不在循环结构。
> 画成两个循环会导致实现出两套控制流，那是错的。

## 2.5 tool-calling 循环（引擎）

先前的架构图画的是**解剖结构**，漏了**引擎**。补上。

### 内循环 —— 与 coding agent 的标准循环一字不差

    while True:
        ① 装配上下文
             系统提示 + memory/MEMORY.md 索引 + preferences.md + 本歌 notes.md
             + state.inspect() 现算的六步状态 + 上一次 tool_result + 对话
        ② 模型输出（文本 或 tool_call）
        ③ 没有 tool_call → 退出，交回创作者
        ④ 执行工具：校验哈希 → 备份 → 原子写 → checkpoint 进日志
        ⑤ 写后钩子自动跑相关检查
        ⑥ tool_result 回灌 → 回到 ①

外循环是创作者：听 → 说一句 → 新一轮。

### 唯一的不同在 ⑥

**`tool_result` 里带可程序化的度量。**

    findings 前后对比 · 对齐偏移 ms · 相似度四维 · 改了几个音符 · 备份路径

所以**模型不需要判断正确性** —— 它只看数字决定下一步。
六个对照项目（含 DAWZY）的 `tool_result` 都只说「执行成功 / 失败」。
这一层是我们独有的，也是整个架构成立的支点：
模型负责品味，L1 负责正确。

### 上下文压缩落在 ①

**保留完整上下文直到接近模型窗口上限**（1.8 ④ 修正过：不由成本触发）。
journal 是持久记忆，但它不是「丢弃上下文的借口」—— token 不稀缺。
这条规则让长会话不退化，而且不需要「总结」这种会丢信息的压缩。

### 四个退出条件

| | 条件 | 现状 |
|---|---|---|
| 1 | 模型不再调工具（自然结束） | ✅ 天然有 |
| 2 | 达到 `auto_rounds_before_handback`（默认 1） | 新建 |
| 3 | 超预算：`max_total_actions=5` 或 `budget_s=180` | ❌ **建造第 1 项** |
| 4 | stop 文件出现（创作者叫停） | ❌ **建造第 1 项** |

3 和 4 缺失就是「卡死」的直接来源，所以排在建造顺序最前面。

## 3. 分层

    ┌─ 横切：钩子（写后自动检查）· 鲁棒性 · 只追加日志
    │
    F   前端      对话（已有）· 仪表盘（在建）· 薄 CLI（第 9 项）
    ────────────  ↑ 只渲染，不计算 ────────────────────────────
    L4  记忆层    五层，按写入权限分                    ← 新建
    L3  编排层    意图解析 · 诊断 · 循环 · 预算 · 提案   ← 新建
    L2  工具层    10 个动作，带 schema                  ← 新建
    L1  能力层    六步 + 八项检查 + 修复循环             ← 已建
    L0  文件层    唯一真相来源

**L0 是唯一真相来源。** 状态永远从文件现算，不缓存。代价是每次观察读文件，
换来的是崩溃不丢状态、创作者手改也不会让 agent 认错。

**L1 已经最厚，且不需要模型。** 所以接上模型之后，
**模型只负责品味，正确性由 L1 保证**。

### 横切规则：前端只渲染，不计算（[ADR-0012](adr/0012-observation-surface-before-driving-surface.md)）

借 Pi 的「一个库 + 多个前端」。**业务逻辑只许在库里。**
需要一个新数字，去库里加，不在前端算。

理由是 [ADR-0011](adr/0011-drop-fl-bridge-from-v1.md) 记的那个 bug 模式 ——
两个入口各自实现同一段分析，产出 0.340 和 0.360，**两边都不报错**。
前端要是自己算一遍，它和 `state.inspect()` 迟早对不上，
而且没人会发现：没有人会去比对一个「只是显示」的界面。

这条**从第 1 项就守**，不等到第 9 项。第 9 项做的是「把 CLI 抽出来」；
纪律要是没从头守，那时候就变成重构而不是抽取。

有自动判据：让库返回一个它自己算不出来的数，前端照抄就对，自己算就露馅
（`tests/test_dashboard.py`）。

## 4. 模型（Mistral）的职责边界

| 模型**负责** | 理由 |
|---|---|
| 生成歌词 | 唯一真正需要语言能力的环节 |
| 解析意图 | 「副歌太平」→ 诉求类别 |
| 在多个假设间排序 | 有指标做依据，只排序不判断 |
| 组织交回创作者的说明 | 让他看得懂发生了什么 |

| 模型**不负责** | 理由 |
|---|---|
| 判断正确性 | 八项检查判。模型说「没问题」不算证据 |
| 生成旋律音高 | 声调约束可计算；模型会破坏可复现。**保留接口，列 v2** |
| 写显式偏好 | 那是创作者的规则 |
| 决定何时停 | 预算参数决定，不给自由裁量 |

旋律不交给模型的依据：确定性生成器已被验收两次且七项检查 0 finding。
已知弱点（`interval` 相似度 0.82–0.93）是**动机覆盖率**问题，
不是「需要模型」的证据。一次只引入一个变量。

## 4.5 LLM 接入（Mistral · 2026-08-23 实测）

工作区 `cybererosai`，模型 `mistral-large-2512`。

### 先验四件事，再写代码

| 项 | 结果 |
|---|---|
| 认证 | ✓ 0.44s，可用模型 56 个 |
| 最大款 | `mistral-large-2512`（`mistral-large-latest` 指向它） |
| 中文生成 | ✓ 命题写词 1.1s / 64 tokens，字数与韵脚都听话 |
| **tool calling** | ✓ `finish_reason = tool_calls`，参数结构正确 |

tool calling 这条是**引擎能不能跑起来的前提** —— §2.5 的内循环整个建在它上面。
所以先验它，而不是先写代码再发现不支持。

### 一个推翻既有假设的测量：**贵的是往返，不是 token**

    x-ratelimit-limit-req-minute       4          ← 真正的约束
    x-ratelimit-limit-tokens-minute    250,000    ← 基本用不完

6 路并发立刻吐 2 个 429。串行 1 秒一次也全是 429。稀疏探测确认是
**每 60 秒固定 4 次**，用完归零、整分钟重置（remaining 走 3→2→1→0→3，
9 次探测跨 139 秒全过 = 3.9 次/分钟）。

两个数一除就是这条：**平均每次请求可以带 62,500 tokens。**

| 原来打算的做法 | 现在必须的做法 |
|---|---|
| 内部池 20 版词 = 20 次请求 | **1 次请求返回 20 版** |
| 3 个假设 = 3 个子 agent 各自发请求 | **1 次请求返回 3 个方案** |
| 上下文压缩省 token | **不压缩**，把请求塞满才划算 |
| 自查再来一次请求 | 能合进同一次就合 |

**§8 的 `hypothesis_parallel` 因此换了含义**：不是并行发请求（那必然限流），
而是**一次请求里要多个结果**。并行仍然存在，只是并行发生在模型内部。

### 这条约束怎么换算成墙钟

`budget_s = 300` 配 4 次/分钟 ⇒ **一轮上限约 20 次 LLM 请求**。
`max_total_actions = 8` 若每个动作各占一次往返，光排队等配额就 2 分钟。
所以「一次请求做尽量多的事」不是优化，是**能不能在预算内跑完**的前提。

### 限流值不写死

每个响应都带 `x-ratelimit-limit-req-minute`。
**客户端从响应头读当前上限，不硬编码 4** —— 创作者哪天升到付费档，
agent 自己就跟上，不用改代码。

退避策略也跟着变：**命中 429 就等到下一个整分钟**，不用指数退避 ——
窗口是固定的 60 秒边界，指数退避只会等过头。

### 凭据

    E:/sv-bridge/.env           MISTRAL_API_KEY=...    已被 .gitignore 忽略
    E:/sv-bridge/.env.example   空值模板                进仓库

**三条硬规则**（这个仓库是公开的）：

1. key 只从环境变量 / `.env` 读，**绝不写进任何进 git 的文件**
2. **绝不写进 `journal.jsonl`**，绝不渲染进 `dashboard.html`
3. 报错要脱敏：`Authorization` 头一律打成 `Bearer ***` 再打印

> 这份 key 曾以明文出现在对话记录里。发布前去 Mistral 后台轮换一次最稳妥。

### 依赖：不装 SDK

用标准库 `urllib.request`。理由同 [ADR-0011](adr/0011-drop-fl-bridge-from-v1.md)：
这条链上每少一个依赖就少一个会坏的东西。而我们需要的只是
「POST 一个 JSON、读响应头、处理 429」—— 标准库够了。

## 5. 动作池（L2）

每个动作必须：**幂等** · **写前备份** · **写前校验文件哈希** · **产出可度量**。

| 动作 | 参数 | 现状 |
|---|---|---|
| `gen_lyrics` | 主题 / 版本数 / 避开的既有作品 | 需要模型 |
| `gen_melody` | scope=全曲 \| **段落** · keep=[...] | **段落级要改 `melodize`** |
| `gen_harmony` | kind · sections | 已有 |
| `gen_accompaniment` | groove 组合 | 已有 |
| `tune` | scale · TuneCfg 覆盖 | 已有 |
| `mix` | profile · carve | 已有 |
| `adjust_spec` | 调 / 音区 / 节奏细胞 / 动机 → 重生成 | 参数已有，缺封装 |
| `verify_alignment` | — | 已有 |
| `revert` | 回到日志第 n 步 | 需要日志 |
| `set_mixer_param` | 轨 · 字段 · 值（**窄逃生口**） | 新建，见下 |

**窄逃生口**（借 DAWZY 的代码生成，但收窄）：长尾动作如「第 3 轨声像左移 20%」
不值得各写一个动作。所以开一个只能改**混音器参数**（gain / pan / fxParams）的通道 ——
**它碰不到音符，所以碰不到音乐正确性**，八项检查的约束不会被绕过。
不开放任意代码生成：那会让「每一步可度量」失效。

**`gen_melody(scope=段落)` 是第一版唯一必须新写的能力。**
局部修改是归因的前提；整首重生成之后无法判断改善来自哪一处。

## 6. 诊断层（L3 核心）

**先测，再猜。**

| 创作者会说的 | 指标 | 现状 |
|---|---|---|
| 太平 / 没起伏 | `contour_range` · `dynamic_span` | **两个都要新建** |
| 太像上一首 | uniqueness 四维 | ✅ |
| 机械 / 不像人 | pitchDelta 点数 · 调教点密度 | ✅ |
| 副歌不够爆 | 副歌与主歌的音区差 / loudness 差 / Emotional | ✅ |
| 听不清人声 | 人声与伴奏的中频占比差 | ✅ |
| 咬字 / 倒字 | `check_prosody` | ✅ |
| 太长 / 太短 | 小节数 · 时长 | ✅ |
| 和声感模糊 | 整句与和弦的贴合度 | **第九项检查，缺** |

`contour_range` 与 `dynamic_span` 必须分开：「音高平」和「力度平」修法不同
（前者改 `spec.register` 或轮廓，后者改 `TuneCfg`）。合成一个数就无法归因。

置信度 = 最偏离指标的偏离度 ÷ 第二偏离的。低于 `diagnosis_confidence_floor` 就**问**。

**第一版只启用三条最有把握的规则**（太像上一首 / 机械 / 副歌不够爆），
其余走「问」。诊断是全新一层、零实测支撑，而它做的是用指标猜原因 ——
指标偏低不一定就是原因。宁可多问，不要瞎改。

## 6.5 会话树（第一版就做，创作者 2026-08-23 拍板）

我原本建议第一版只做线性回退。**创作者推翻了，而且他对** ——
我漏看了一个协同效应：

> **做了树，否决记忆的数据结构就自然有了。**
> 每个打了 `rejected` 的分支就是一条负样本，带完整规格特征 + 他的原话。
> 我原来把「否决记忆」当成要单独设计的东西，其实它就是树上的一类节点。

### 树几乎是免费的

因为日志本来就设计成「只追加 + 带父指针」。线性与树的差别只有三件：

1. 一个 `HEAD` 指针（当前在哪个节点）
2. `checkout(id)`：恢复文件 + 移动 HEAD
3. 分支是**隐式**的 —— HEAD 不在最新叶子上时写新节点，自然产生分支

### 真正的难点不是树，是 checkpoint 的完整性

**一个节点必须能完整恢复项目状态。** 如果 checkpoint 只快照 `.svp`，
切回旧节点时 `lyrics.txt` 还是别的分支的 → 状态不一致，而且**不会报错**。

所以 **checkpoint 是全套项目文件的快照**，不是「改了哪个就存哪个」。
代价可以接受，但要区分大小文件：

| 文件 | 大小 | 怎么存 |
|---|---|---|
| `lyrics.txt` · `project.json` · `notes.md` · `.svp` · `.mid` | 合计约 130 KB | **每个节点全量复制** |
| 伴奏 `.wav` | 31 MB | **按内容寻址**：`blobs/<sha256>.wav`，节点只存哈希 |

### 目录结构

    songs/<slug>/
      journal.jsonl              只追加，每行一个节点
      HEAD                       当前节点 id
      checkpoints/<node_id>/     全套小文件 + manifest.json（含 wav 哈希）
      blobs/<sha256>.wav         大文件去重存储

### 节点记什么

    {
      "id": "n0042",  "parent": "n0041",  "ts": "...",
      "label": "重生成副歌（音区抬高 3 度）",      ← **必须可读，否则树无法导航**
      "action": "gen_melody",
      "params": {"scope": ["副歌1","副歌2"], "keep": ["主歌1","主歌2"]},
      "metrics_before": {...},  "metrics_after": {...},
      "verdict": null | "accepted" | "rejected",
      "verdict_note": "太满了",                   ← **否决记忆的原料**
      "spec_snapshot": {调, 音区, 动机, 节奏细胞}, ← 让否决可泛化
      "checkpoint": "checkpoints/n0042"
    }

`label` 是硬要求。没有可读标签的树无法导航 —— 一堆 `n0041` 对创作者毫无意义。

### 操作

| 操作 | 语义 |
|---|---|
| `log --tree` | 画出树，标注 HEAD 与每个节点的裁决 |
| `checkout <id>` | 从 checkpoint 恢复全套文件，移动 HEAD |
| `label <id> <文本>` | 给节点命名 |
| `verdict <id> accepted\|rejected [原话]` | 记录裁决。**这是否决记忆的写入口** |
| `pick <from_id> <段落>` | **取另一节点的某个段落**，见下 |

### 不做 merge，做 cherry-pick

「回到上一版的副歌，但保留现在的调教」—— 这听起来像 merge，但**不是**。

我们的状态是**结构化**的（音符按段落组织），所以不需要 git 式的三方合并，
只需要「取节点 X 的第 N 段」。`pick(from_id, scope)` 语义明确、不会冲突。

**结构化状态让 cherry-pick 比通用 merge 简单** —— 这是相对 coding agent 的一处优势，
因为代码没有天然的段落边界，而歌有。

## 7. 记忆层（L4）

| 层 | 存什么 | 落地 | 谁能写 |
|---|---|---|---|
| ② 创作日志 | 动作 · 假设 · 度量前后 · 裁决 · **父指针** | `songs/<slug>/journal.jsonl` | agent，只追加 |
| ③ 预设 | 曲式 / 调教档 / 混音档 / 律动 | `memory/presets/*.json` | agent 提取，创作者确认命名 |
| ④a 显式偏好·全局 | 跨歌规则 | `memory/preferences.md` | **只有创作者** |
| ④a 显式偏好·本歌 | 这首歌的特殊要求 | `songs/<slug>/notes.md` | **只有创作者** |
| ④b 推断偏好 | **从创作者的编辑里推断**，自然语言写，按题材检索 | `memory/inferred/<题材>.md` | agent 写，**创作者可随时改掉** |
| ⑤ 环境事实 | 技术约束 | `memory/facts.md` | agent 踩到就写 |
| — | 索引，每次会话加载 | `memory/MEMORY.md` | agent 维护 |

### 三条硬规则

1. **日志只能追加**，且带父指针（为将来的树留格式）。它是归因的唯一依据。
2. **agent 绝不能写 ④a。** 否则它把自己的推断固化成创作者的规则 ——
   越来越固执且错。**日志 → 预设 可以，日志 → 显式偏好 不可以。**
3. **④b 改成从「编辑」学，不从「接受/否决」学**（借 PRELUDE，见 1.5 节）。
   原判断是「2 首接受、1 次否决，推不出结论，第一版留空」。但创作者一直在
   直接编辑 `lyrics.txt` —— **每次编辑都是信号，且比二选一丰富得多**。
   写成自然语言而非特征向量，理由是他能看见并纠正；按题材检索而非一个全局偏好。
   **这是值得试的方向，不是已验证的方法**（原论文用模拟用户评估）。

| `propose_before_act` | True | Plan mode：先提案 |
| `writable_paths` | `songs/<slug>/`、项目 svp/mid | 环境隔离式权限 |

## 11. 建造顺序

| 序 | 做什么 | 为什么在这 | 状态 |
|---|---|---|---|
| **1** | 原子写 · **checkpoint 全套快照** · 文件哈希校验 · 可中断 · 循环超时 | 五件都是**文件写入的正确性**，必须一起做。会话树进第一版之后，「checkpoint 只存改动文件」会造成**不报错的状态不一致** —— 与原子写同类问题 | **✅ 2026-08-24** |

| **3** | **会话树**：journal + HEAD + `checkout` / `label` / `verdict` + `blobs/` 去重 | 升为独立一项（创作者拍板进第一版）。**必须在任何动作之前**，否则第一个动作就没有节点可挂 | **✅ 2026-08-25** |
| 4 | ⑤ 环境事实归集（现在散在十几个 docstring 里） | agent 读不到就等于没有 | **✅ 2026-08-25** |

| 6 | `gen_melody(scope=段落)` + `pick(from_id, scope)` | 两者共用「按段落取音符」这套逻辑，一起做 | ← 下一个 |
| 7 | 两个新指标（`contour_range` / `dynamic_span`）+ 第九项检查 | 诊断的原料 | — |
| 8 | 诊断层 + **并行假设（子 agent）** + Plan mode 提案 | 并行是 1.8 节的直接后果：用实测取代排序猜测 | — |
| 9 | 库化 + 薄 CLI + 斜杠命令 | 让「换 orchestrator」变成换前端 | — |
| 10 | 接 Mistral | 最后接，出问题才能确定是模型的问题 | — |

## 12. 验收判据

1. **模式 A**：给一句主题，除 FL 三步手动外全程不需要人手工串脚本
2. **模式 B**：对三个真实诉求能正确诊断到层、执行一个动作、**如实报告改善或没改善**
3. **鲁棒性**：kill 进程后状态正确；任一动作连跑两次结果一致；
   **手改 `.svp` 后 agent 拒绝覆盖而不是静默盖掉**
4. **日志**：每个动作可回溯，能回滚到任意一步
5. **诚实性**：置信度低时确实去问，而不是猜
6. **控制感**（借 DAWZY 的评估维度）：创作者是否感到自己在掌控
   —— 每次修改前有提案、每次改动可回滚、每次结论有证据

第 5 条最容易在实现时丢掉，所以单列。
第 6 条是唯一非技术判据，但它决定这东西会不会被继续用。

## 14. fork4 的第一件事

按第 11 节，从**地基三项**开始，且顺序不能换：

    1  原子写 + checkpoint 全套快照 + 哈希校验 + 可中断 + 超时
    2  幂等性测试（同一动作连跑两次结果必须一致）
    3  会话树（journal + HEAD + checkout/label/verdict + blobs 去重）

**第 3 项必须在任何 agent 动作之前完成** —— 否则第一个动作就没有节点可挂，
而日志事后补不了。

现有的六步脚本在地基做完之前**保持可用**，不要为了重构而中断它们：
《晓风残月》必须始终能重跑。
