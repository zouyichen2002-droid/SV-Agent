## 5. 上游 SynthVCopilot 调研（2026-09-16 实测，以代码为准）

组织现有 **6 个公开仓库**，比八月多了两个。方向已明确转向**翻唱**。

### 5.1 已实现、可用

| 组件 | 实际能力 |
|---|---|
| `synthv-agent-bridge` | 67★/10 fork，今天仍在推，v0.3.1。9 月新增 **Cover 曲谱支持**、SV1 旧版桥 |
| `pi-audio probe` | 单曲特征指纹：BPM / 调性 / 打击比 / 能量弧 / 音区分布；可选 PANNs 加乐器构成、曲风倾向、有词无词判别；可选 basic-pitch 音符统计 |
| `pi-audio pair-diff` | **有词/无词配对差分 → 单音人声 MIDI**。按 (音高, 起点±容差) 消耗式匹配扣掉伴奏，残差即人声，再「最高音抢占」单音化 |
| FFmpeg 组件 | 受管生命周期（装/更新/卸载）+ 固定用途音频准备与响度操作 |
| CVRS | 跨版本 `.svp` 参考音频助手，克隆结构到新文件；**不渲染、不覆盖源** |
| `synthv-toolbox` | Electron 桌面壳：GUI、组件安装、插件双层授权、SV1/Flat/SV2 统一接口 |
| `SV1_Harmony_API` | SV1 的文件伪总线，双向 JSON，不限语言 |

### 5.2 只登记、未实现（其 README 自承）

本地 Whisper、源分离、完整 Sound-to-MIDI。

**注意一处矛盾**：pi-agent README 说「乐器/曲风分析、节拍检测」未实现，
但 `pi_audio.py` 的 `probe --panns` 做了。差别在于**能力以脚本存在，
但没做成受管组件**（有安装作业与运行时状态的那种）；目前只有 FFmpeg 有完整生命周期后端。

### 5.3 三条硬限制

1. **pi-audio 要 Python ≤ 3.11**（basic-pitch 生态限制），本机是 3.13 → 需单开环境
2. **`pair-diff` 不做源分离** —— 要调用方自备人声与伴奏两条 stem
3. 输出需 **≤512 音符**才能喂桥的 `import_monophonic_score`

### 5.4 值得借鉴的四样（已过滤掉本项目用不上的）

1. **`findings.md` 的因果链格式** —— 上游 `synthv-toolbox/agents/` 下 32 个编号任务目录，
   每个固定三份：`task_plan.md`（勾选清单）/ `progress.md`（操作流水）/ `findings.md`。
   findings 写法：`[类型] -> 观察 -> 所以必须怎样`。记推理链而非结论。
   配套 `tasks.md` 总账表有一列「**变更动机**」。
2. **`unavailableCapabilities`** —— 桥把能力缺口做成机器可读的声明列表，
   运行时主动上报自己做不到什么。与本项目的三色纪律同源，只是用在能力面而非检查上。
3. **组件目录的「已登记 vs 已实现」状态区分** + 受管组件的安全契约
   （FFmpeg：不改全局 PATH、不执行调用方传入参数、不接受远程 URL）。
4. **pi-audio 的设计取向与本项目一致**：「风格命名刻意留给上层 LLM，
   本工具只出结构化事实，不下审美结论」—— 等同于「模型负责品味，检查负责正确」。

**不建议借**：桌面壳、Rust C-ABI DLL、插件双层授权、多宿主兼容。
那些解决的是「分发给第三方」的问题，本项目是单用户单工作流，引入即为架构而架构。

### 5.5 对本项目的两处直接影响

- **`probe` 的输出可直接当语料元数据**（BPM/调性/音区分布/能量弧，每首一条 JSON）。
- **`pair-diff` 纯度无任何公开数字**，且是音符级相减，同时继承 basic-pitch 在两条 stem 上的误差。
  用它之前须按本项目规矩先注入已知缺陷验证。
  **现成对照样本**：《潮声回响》轨 5 的 174 音符时间基经双证据链验证过，可用来量它的纯度。
- **歌词对齐上游完全没有**（Whisper 是空条目），只能用本项目的 CTC。

## 6. 一条被否掉的提议（存档，避免重复讨论）

曾提议「把上游 + 本项目 + DeepSeek Harness 三者各取一部分，重开一个新项目」。
**结论：不重开。** 理由：

1. 会拆掉唯一在跑的东西（242 测试、13 ADR、909 首校准数据 —— 最难复制的不是代码，是那套纪律和校准积累）
2. dsh 是 developer preview，README 自己宣告**会有破坏性变更**；
   把「门槛稳定」的项目建在会破坏兼容的基座上是自相矛盾
3. 使用者仍在逆向学习 dsh（阶段二），违反其自己的「先框架再 commit」原则
4. **取一部分 ≠ 新仓库** —— 借格式就是写个文件，借抽象要么自己实现要么当依赖

什么证据会推翻：dsh 出稳定版，**且**本项目真的出现第三方插件生态需求。
