## 0. 为什么现在写这个

**这个项目到今天为止有零个自动化测试。** 八项检查、六项校验、对齐验证
都是「跑一次看输出」，没有一个能在改动之后自动告诉我「你弄坏了什么」。

而 agent 阶段每一步都会让它跑更多轮、改更多东西。没有测试，
「未验证」在本项目已经反复等于「大概有 bug」：

- 声称注入 8 个缺陷，实际只落地 6 个（分项里根本没有 phrase）
- `fl_ping` 返回 `alive: False`，体检照样打印「全部就绪」
- 「出界就移八度」把低八度变成同音齐唱
- 句长独立随机 → 同轨重叠 57 处 + 11.5 秒断气音

这四个都是**跑通了但结果是错的**。所以判据必须是**可自动判定的**，
不能是「看起来对」。

---

## 1. 创作者的验收方式：看仪表盘，不看测试输出

创作者不读代码。所以「这一步做对了吗」的答案必须是**他能看见的**。

**每个建造项的验收都要在仪表盘上有对应的可视证据**，见第 4 节。
测试脚本给我用，仪表盘给他用，两者读的是同一批文件。

## 2. 四层测试

| 层 | 测什么 | 判据形态 | 跑多久 |
|---|---|---|---|
| **单元** | 纯函数：blicks 换算 · 和弦级数 · 节奏细胞 · 调内音级移动 | 断言相等 | 秒级 |
| **属性** | **幂等 · 原子 · 可复现** —— 不测具体值，测性质 | 性质成立 | 秒级 |
| **回归** | 两首歌必须始终跑出**相同结果**（黄金文件） | 逐字段比对 | 分钟级 |
| **端到端** | 模式 A 走完六步；模式 B 三个诉求 | 见 §5 | 分钟级 |

### 属性测试是这个项目最需要的一层

因为上面列的四个真 bug，**没有一个能被「跑一次看输出」抓到**，
但全都能被属性测试抓到：

| 属性 | 表述 | 会抓到哪个历史 bug |
|---|---|---|
| **幂等** | 同一动作连跑两次，产物语义相同 | 调教点会不会叠加两遍（未验证） |
| **原子** | 任意时刻 kill，文件要么完整旧的要么完整新的 | 写一半崩掉 |
| **可复现** | 同种子同输入 → 同输出 | `hash()` 每进程加盐（已修） |
| **不重叠** | 任一轨内音符不重叠 | 同轨重叠 57 处 |
| **不越界** | 任一音符时长 ≤ 上限、音高在音域内 | 11.5 秒断气音 |
| **和声非同音** | 和声轨与主旋律同时刻不同音 | 假和声 |
| **检查会响** | 注入缺陷必须被检出（敏感度） | 声称 8 个实际 6 个 |

**最后一条最重要**：只报 0 的检查不算检查。每个检查项都要有配套的
「注入这个缺陷 → 必须报出来」的反向测试。

## 4. 十个建造项的验收判据

每项都给：**自动判据**（我跑）+ **可视证据**（你看）。

| # | 建造项 | 自动判据 | 仪表盘上你看得见什么 |
|---|---|---|---|
| **1** | 原子写 · checkpoint 全套 · 哈希校验 · 可中断 · 超时 | 写入过程中 kill，文件非半成品（重复 20 次）· 手改 `.svp` 后写入被拒并报哈希不符 · 建 stop 文件后下一轮退出且无半成品 · `budget_s=1` 时一个动作后退出 | **安全状态面板**：五项各一个灯；手改工程后刷新，哈希那一项变红并显示「文件被外部修改」 |
| **2** | 幂等性测试 | 每个动作连跑两次，产物语义相同（uuid 除外） | **动作表**：每个动作一行，标「幂等 ✓/✗」 |
| **3** | 会话树 | 建 3 分支 → 逐个 checkout → `state.inspect()` 与当时一致 · journal 行数单调增 · 同一 wav 在 blobs 里只存一份 | **树视图**：分支、HEAD、每个节点的裁决与度量。**这是你最常看的一屏** |
| **4** | ⑤ 环境事实归集 | `facts.md` 覆盖已知的六条硬约束 | **约束清单**面板 |
| **5** | 工具层 + 写后钩子 | 每个动作有 schema 且能被校验 · 任意写入后钩子必然跑（用故意失败的动作验证） | **动作日志**：每次调用的参数、耗时、钩子结果 |
| **6** | `gen_melody(scope=段落)` + `pick` | 只重生成副歌时，主歌音符**逐字段不变** · `pick` 后目标段落与源节点逐字段相同 | **改动高亮**：哪些小节被改了，改了几个音符 |
| **7** | 两个新指标 + 第九项检查 | 每个指标有敏感度测试（人为造出「平」必须被测出） | **指标面板**：八项检查 + 三个新指标的当前值与阈值 |
| **8** | 诊断 + 并行假设 + Plan mode | 三个诉求各有一个已知答案的场景，诊断必须指对层 · 置信度低时必须问而不是猜 | **诊断面板**：三个假设并排、各自度量、选了哪个、为什么 |
| **9** | 库化 + CLI + 斜杠命令 | 同一操作经库调用与经 CLI 调用结果相同 | — |
| **10** | 接 Mistral | 换掉 orchestrator 后，模式 A 端到端仍通过 | **模型面板**：本轮 token、调用次数、限流退避次数 |

### 第 8 项的判据要特别说

诊断是全新的一层，**零实测支撑**。所以它的验收不是「诊断准确率」，而是：

1. 三个已知答案的场景（人为把副歌音区压窄 / 复制上一首的节奏细胞 /
   清空调教）—— 诊断必须指对层
2. **置信度低时必须去问，而不是猜。** 这条比准确率重要 ——
   一个会说「我不确定」的诊断层是可用的，一个自信瞎猜的不是

## 5. 端到端验收（第一版完成的标准）

1. **模式 A**：给一句主题，除 FL 三步手动外，全程不需要人手工串脚本
2. **模式 B**：三个真实诉求能诊断到层、执行一个动作、**如实报告改善或没改善**
3. **鲁棒性**：kill 后状态正确 · 动作连跑两次结果一致 ·
   **手改 `.svp` 后拒绝覆盖而不是静默盖掉**
4. **会话树**：能建分支、切回、cherry-pick 某段落
5. **诚实性**：置信度低时确实去问
6. **掌控感**（借 DAWZY 的评估维度）：创作者能随时看懂
   「它现在在做什么、为什么、改了什么、怎么撤销」

第 5、6 条最容易在实现时丢掉，所以单列。

## 6. 可视化平台的设计

### 形态：agent 生成的单个 HTML 文件

    songs/<slug>/dashboard.html      每次动作后重新生成，浏览器里自动刷新

**为什么不是 Web 应用**：

| | 单 HTML 文件 | Web 应用（前后端） |
|---|---|---|
| 依赖 | 零 | 服务器 · 端口 · 框架 |
| 与真实状态的关系 | **从文件渲染，不可能不一致** | 有自己的状态，会漂移 |
| 崩溃后 | 重新生成即可 | 要重启服务 |
| 归档 | 可以进 checkpoint，回看历史某一刻的界面 | 不行 |

这条和「状态从文件现算，不缓存」是同一条原则。
**仪表盘是文件的视图，不是另一个真相来源。**

### 五个面板

| 面板 | 内容 | 对应哪个建造项 |
|---|---|---|
| **状态** | 六步 · 每步谁做 · 阻塞原因 | 已有 `state.inspect()` |
| **会话树** | 分支 · HEAD · 每节点的裁决与度量 | 第 3 项 |
| **本轮** | 诊断 → 假设 → 动作 → 度量前后对比 | 第 5、8 项 |
| **指标** | 八项检查 + 三个新指标，当前值与阈值 | 第 7 项 |
| **安全** | 原子写 · 哈希 · 可中断 · 超时 · 幂等，各一个灯 | 第 1、2 项 |

### 第一版只读

点击节点 checkout 需要服务器。**第一版所有操作仍在对话里说**
（「回到 n06」「这版不行」），仪表盘只负责让你**看懂**。
这符合「创作者用自然语言驱动」的定位。

### 建造方式：随每一项增量长出来

不单独排一个「做仪表盘」的建造项。**每完成一个建造项，就给仪表盘加对应的面板** ——
这样它从第一天起就有用，而且永远反映真实存在的东西，不会画出还没做的功能。

---

## 7. 不做什么

- 不做测试覆盖率指标（这个规模上是噪声）
- 不做 CI（本地项目，`regression.py` 一条命令足够）
- 不做仪表盘的交互操作（第一版只读）
- 不测 SynthV / FL 本身的行为（那是外部软件）
