## 0. 为什么现在写这个

**这个项目到今天为止有零个自动化测试。** 八项检查、六项校验、对齐验证
都是「跑一次看输出」，没有一个能在改动之后自动告诉我「你弄坏了什么」。

而 agent 阶段每一步都会让它跑更多轮、改更多东西。没有测试，
「未验证」在本项目已经反复等于「大概有 bug」：

- 声称注入 8 个缺陷，实际只落地 6 个（分项里根本没有 phrase）
- `fl_ping` 返回 `alive: False`，体检照样打印「全部就绪」
- 「出界就移八度」把低八度变成同音齐唱
- 句长独立随机 → 同轨重叠 57 处 + 11.5 秒断气音

这四个都是**跑通了但结果是错的**。所以判据必须是**可自动判定的**，
不能是「看起来对」。

## 1. 创作者的验收方式：看仪表盘，不看测试输出

创作者不读代码。所以「这一步做对了吗」的答案必须是**他能看见的**。

**每个建造项的验收都要在仪表盘上有对应的可视证据**，见第 4 节。
测试脚本给我用，仪表盘给他用，两者读的是同一批文件。

## 2. 四层测试

| 层 | 测什么 | 判据形态 | 跑多久 |
|---|---|---|---|
| **单元** | 纯函数：blicks 换算 · 和弦级数 · 节奏细胞 · 调内音级移动 | 断言相等 | 秒级 |
| **属性** | **幂等 · 原子 · 可复现** —— 不测具体值，测性质 | 性质成立 | 秒级 |
| **回归** | 两首歌必须始终跑出**相同结果**（黄金文件） | 逐字段比对 | 分钟级 |
| **端到端** | 模式 A 走完六步；模式 B 三个诉求 | 见 §5 | 分钟级 |

### 属性测试是这个项目最需要的一层

因为上面列的四个真 bug，**没有一个能被「跑一次看输出」抓到**，
但全都能被属性测试抓到：

| 属性 | 表述 | 会抓到哪个历史 bug |
|---|---|---|
| **幂等** | 同一动作连跑两次，产物语义相同 | 调教点会不会叠加两遍 —— **2026-08-24 已验：612 → 612，不叠加** |
| **原子** | 任意时刻 kill，文件要么完整旧的要么完整新的 | 写一半崩掉 |
| **可复现** | 同种子同输入 → 同输出 | `hash()` 每进程加盐（已修） |
| **不重叠** | 任一轨内音符不重叠 | 同轨重叠 57 处 |
| **不越界** | 任一音符时长 ≤ 上限、音高在音域内 | 11.5 秒断气音 |
| **和声非同音** | 和声轨与主旋律同时刻不同音 | 假和声 |
| **检查会响** | 注入缺陷必须被检出（敏感度） | 声称 8 个实际 6 个 |
| **显示不过期** | 源文件一变，界面必须跟着变 | 改了歌词页面还是旧字数 |

**最后一条最重要**：只报 0 的检查不算检查。每个检查项都要有配套的
「注入这个缺陷 → 必须报出来」的反向测试。

## 4. 十个建造项的验收判据

每项都给：**自动判据**（我跑）+ **可视证据**（你看）。

| # | 建造项 | 自动判据 | 仪表盘上你看得见什么 |
|---|---|---|---|
| **1** | 原子写 · checkpoint 全套 · 哈希校验 · 可中断 · 超时 | 写入过程中 kill，文件非半成品（重复 20 次）· 手改 `.svp` 后写入被拒并报哈希不符 · 建 stop 文件后下一轮退出且无半成品 · `budget_s=1` 时一个动作后退出 | **安全状态面板**：五项各一个灯；手改工程后刷新，哈希那一项变红并显示「文件被外部修改」 |
| **2** | 幂等性测试 | 每个动作连跑两次，产物语义相同（uuid 除外） | **动作表**：每个动作一行，标「幂等 ✓/✗」 |
| **3** | 会话树 | 建 3 分支 → 逐个 checkout → `state.inspect()` 与当时一致 · journal 行数单调增 · 同一 wav 在 blobs 里只存一份 | **树视图**：分支、HEAD、每个节点的裁决与度量。**这是你最常看的一屏** |
| **4** | ⑤ 环境事实归集 | `facts.md` 覆盖已知的六条硬约束 | **约束清单**面板 |
| **5** | 工具层 + 写后钩子 | 每个动作有 schema 且能被校验 · 任意写入后钩子必然跑（用故意失败的动作验证） | **动作日志**：每次调用的参数、耗时、钩子结果 |
| **6** | `gen_melody(scope=段落)` + `pick` | 只重生成副歌时，主歌音符**逐字段不变** · `pick` 后目标段落与源节点逐字段相同 | **改动高亮**：哪些小节被改了，改了几个音符 |
| **7** | 两个新指标 + 第九项检查 | 每个指标有敏感度测试（人为造出「平」必须被测出） | **指标面板**：八项检查 + 三个新指标的当前值与阈值 |
| **8** | 诊断 + 并行假设 + Plan mode | 三个诉求各有一个已知答案的场景，诊断必须指对层 · 置信度低时必须问而不是猜 | **诊断面板**：三个假设并排、各自度量、选了哪个、为什么 |
| **9** | 库化 + CLI + 斜杠命令 | 同一操作经库调用与经 CLI 调用结果相同 | — |
| **10** | 接 Mistral | 换掉 orchestrator 后，模式 A 端到端仍通过 | **模型面板**：本轮 token、调用次数、限流退避次数 |

### 第 8 项的判据要特别说

诊断是全新的一层，**零实测支撑**。所以它的验收不是「诊断准确率」，而是：

1. 三个已知答案的场景（人为把副歌音区压窄 / 复制上一首的节奏细胞 /
   清空调教）—— 诊断必须指对层
2. **置信度低时必须去问，而不是猜。** 这条比准确率重要 ——
   一个会说「我不确定」的诊断层是可用的，一个自信瞎猜的不是

判据不是「跑通了」，是这些数字：

| 判据 | 实测 |
|---|---|
| 写入中途 kill × 20 | **14 次完整旧内容 · 6 次完整新内容 · 0 个半成品** |
| —— 杀点是否落进写入窗口 | 14 次落进去了。子进程先写就绪信号，父进程再随机毫秒后杀 |
| 手改后写入被拒 | ✓ 抛 `ExternalEdit` 并指名文件，文件原封不动 |
| 全套快照去重 | 5 个快照，逻辑 165 MB → 磁盘 32 MB，**省 80%** |
| 回滚 | 只重写真正变了的文件；账本同步更新 |
| 五个动作幂等 | 全部 ✓。**`step5_tune` 612 → 612 点，不叠加** |
| 归一化敏感度 | 6 个反向测试：音符变 / 点数翻倍 / mixer 变 / 引用结构丢失，都判为不等 |
| 过期检测 | ✓ 会响。碰一下脚本时间戳，动作表表头立刻变红 |

| 判据 | 实测 |
|---|---|
| 建 3 分支 → 逐个 checkout → `state.inspect()` 与当时一致 | ✓ 在《晓风残月》**真副本**上跑，走的是创作者实际看到的观察函数 |

### 第 4 项的实测结果（2026-08-25）

`specs/facts.md` 共 **15 条**硬约束（验收标准要求覆盖六条）。
分布：**6 条快速复验通过 · 1 条 slow · 1 条 network · 7 条只有出处**。

关键设计不是「把事实抄下来」，而是：

> **能自动复验的事实，就必须自动复验。**

一份没人复查的约束清单，和只报 0 的检查是同一类东西。写清单的当天
就靠这条抓到一处记错：我一直以为 `mido` 构造中文轨名就崩，
实际是 `save()` 才崩（F08）。**按错的版本去防，会防在错的地方。**

顺带被测试抓到的一处自伤：约束清单面板一开始是**每次渲染现跑复验**，
于是 `test_渲染是纯函数` 挂了 —— mtime 碰撞率每次都不一样。
而且监视模式下每秒重渲一次意味着每秒 spawn 三个子进程、写 200 次文件。
改成读落盘报告。**我自己违反了「前端只渲染，不计算」，测试替我抓住了。**

### 第 5 项的实测结果（2026-08-25）

**11 个动作**（架构文档 §5 列了 10 个，`assemble` 是工作流需要而补的第 11 个），
其中 8 个完全可用、2 个部分可用、1 个待接模型。导给模型 10 个 ——
**没接上的不导**，放一个必然失败的工具进去只会换来一次浪费的调用。

| 判据 | 实测 |
|---|---|
| 每个动作有 schema 且能被校验 | ✓ 自带校验器，不引入 jsonschema。缺必填/类型错/枚举外/越界/多余参数**五种都会响** |
| **任意写入后钩子必然跑** | ✓ 用「写完就抛异常」的动作验证：钩子照跑，且留下可回退节点 |
| 动作没写文件就不跑钩子 | ✓ 触发条件是**文件指纹变了**，不是动作的自我报告 |
| 钩子失败不掩盖 | ✓ 造一处同轨重叠：动作 ok、钩子报 ✗，两个分开呈现 |
| 外部改动时拒绝执行 | ✓ 且拒绝之后不动任何文件 |
| 每个动作之前树上有可回退节点 | ✓ 没有 HEAD 就先建基线，脏了就先自动存 |
| `tool_result` 带度量 | ✓ `delta` 只报变了的项；`加一个音符` → `notes.change = 1` |
| 窄逃生口碰不到音符 | ✓ 写完断言音符数不变；越界字段与不存在的轨都会报出可用清单 |

#### 三处顺带修掉的「两个实现」

这一项要读很多既有能力的数字，于是逼出三处重复实现：

| 原来 | 现在 |
|---|---|
| 对齐计算在 `step5_assemble.main()` 里内联 | 抽成 `align_report()`，脚本与钩子**同一个实现**。抽完数字一模一样：−1.0 ms / 0.8 ms |
| 同轨重叠在 `state.inspect` 里内联 | 抽成 `idem.count_overlaps()`，观察函数与钩子共用 |
| 幂等列靠动作名模糊匹配脚本名 | 每个动作显式写出它封装哪个脚本 |

第三处尤其典型：模糊匹配**匹配错了也不会报错**。

#### 一个实测发现

`step5_tune` 重写 `.svp` 之后**字节完全相同** —— 比第 2 项测到的语义幂等更强。
于是执行器判定「文件没变」，不留节点也不跑钩子。**这是对的**：
一棵长满空节点的树会让「哪一步真的改了东西」变得无法辨认。

#### 写后钩子当场抓到的两个真 bug

第 5 项刚建好的钩子，在第 6 项第一次跑就抓到东西：

| bug | 钩子报的 | 根因 |
|---|---|---|
| 拼进来的副歌满是调外音 | `checks` 报 **19 finding（scale 13）** | 新候选按**自己的调**生成，把 G 小调的副歌拼进 D 小调的歌。锁定现有调性后 19 → 1 → 默认候选池 **0** |
| 局部修改把下游全冲了 | `delta` 报 `steps_done 6→4`、`tuning_points 1224→0`、`audio_tracks 1→0` | `write_project` 从**空模板**重建，音频轨、混音、调教全丢。补了 `carry_over()` |

**这两个都不可能靠「跑一遍听听」发现** —— 工程照样打开、照样能唱。
它们是第 5 项那个「tool_result 带数字」的第一份回报。

#### 一条刻意保留的破坏

`carry_over()` **只在音符逐字段没变时才搬回调教**。副歌重生成之后，
主旋律那一轨的调教会被丢弃 —— 因为曲线按时间锚定，
音符换了还留着等于把颤音挂在错的字上，**比丢了更难发现**。

但丢弃必须看得见：测试断言 `delta` 里必须出现 `tuning_points` 掉到 0。
这个项目里「安静地少了点东西」是最贵的一类错误。

#### 前两项自己暴露出来的三个 bug

全都是「安静地出错」，没有一个能被「跑一遍看输出」抓到：

| bug | 怎么发现的 | 后果 |
|---|---|---|
| 仪表盘是快照不是视图 | **创作者跑测试 ② 时抓到** | 页面理直气壮显示两小时前的数字 |
| 指纹只看 mtime | 修复的测试挂了 | 本机 59% 概率两次写 mtime 相同，同长度改动骗过监视器 |
| `Guard` 缓存账本 | 新写的测试挂了 | 两个实例同时活着，后写的把前一个的记录整片盖掉 |

第一个是创作者发现的，第二、三个是**测试在我写修复的时候当场抓到的** ——
这正是第 2 项排在这个位置的理由：它是第一个会自动告诉我「你弄坏了什么」的东西。

#### 顺带补的两个不变量

- **任何会丢失当前内容的操作之前，必须先有一张快照。** `--adopt` 与 `--restore`
  都会自动拍。创作者第一次实跑时，他在 SynthV 里的版本就是靠这条存住的
- **`--adopt` 必须如实报告它在采纳什么。** 它是唯一销毁「被外部改过」这个信号的
  操作，所以不许沉默

## 5. 端到端验收（第一版完成的标准）

1. **模式 A**：给一句主题，除 FL 三步手动外，全程不需要人手工串脚本
2. **模式 B**：三个真实诉求能诊断到层、执行一个动作、**如实报告改善或没改善**
3. **鲁棒性**：kill 后状态正确 · 动作连跑两次结果一致 ·
   **手改 `.svp` 后拒绝覆盖而不是静默盖掉**
4. **会话树**：能建分支、切回、cherry-pick 某段落
5. **诚实性**：置信度低时确实去问
6. **掌控感**（借 DAWZY 的评估维度）：创作者能随时看懂
   「它现在在做什么、为什么、改了什么、怎么撤销」

第 5、6 条最容易在实现时丢掉，所以单列。

## 6. 可视化平台的设计

### 形态：agent 生成的单个 HTML 文件

    songs/<slug>/dashboard.html      每次动作后重新生成，浏览器里自动刷新

**为什么不是 Web 应用**：

| | 单 HTML 文件 | Web 应用（前后端） |
|---|---|---|
| 依赖 | 零 | 服务器 · 端口 · 框架 |
| 与真实状态的关系 | 从文件渲染，**不会算出第二个数**（但会过期，见下） | 有自己的状态，会漂移 |
| 崩溃后 | 重新生成即可 | 要重启服务 |
| 归档 | 可以进 checkpoint，回看历史某一刻的界面 | 不行 |

这条和「状态从文件现算，不缓存」是同一条原则。
**仪表盘是文件的视图，不是另一个真相来源。**

### 但它是快照，不是视图 —— 必须有监视模式

**2026-08-23 实测打脸。** 创作者手改 `lyrics.txt` 之后刷新页面，
字数纹丝不动 —— 因为 `dashboard.html` 是静态文件，浏览器重读的还是那一份，
**没有任何东西在源文件变化时重新生成它**。当时页脚上还印着
「所以它不可能和真实状态对不上」。

错在把两件事混成了一件：

| 保证 | 靠什么 | 成立吗 |
|---|---|---|
| 不会和库**算出两个不同的数** | 前端只渲染不计算 | ✓ 成立 |
| 不会**过期** | ——什么都没有 | ✗ 当时不成立 |

修法两条，缺一不可：

1. **监视模式** `--watch`：盯住 `proj.sources` 的六个文件，一变就重生成。
   来源列表由**库**给（`SongProject.sources`），写死在前端迟早漏一个
2. **页面自己说实话**：静态快照就印「静态快照 · 不会自己更新」，
   监视中才印「监视中」。**不许让人以为看的是实时状态**

> 顺带被测试抓到的第二个洞：指纹一开始用 `mtime`，
> 而本机连续两次写有 **59%** 的概率 mtime 完全相同（Windows 时钟刻 ~15 ms）。
> 换一个同字节长度的字就能骗过它 —— 差一点用一个同样安静的失败
> 换掉原来那个。改成小文件按内容哈希、大文件按 (mtime, size)。

**这是本项目第三次「显示层安静地说了假话」**（前两次：`audio.py` 的
0.340/0.360、`fl_ping` 的假阴性）。所以它进 §2 的属性表：

### 第一版只读

点击节点 checkout 需要服务器。**第一版所有操作仍在对话里说**
（「回到 n06」「这版不行」），仪表盘只负责让你**看懂**。
这符合「创作者用自然语言驱动」的定位。

### 建造方式：随每一项增量长出来

不单独排一个「做仪表盘」的建造项。**每完成一个建造项，就给仪表盘加对应的面板** ——
这样它从第一天起就有用，而且永远反映真实存在的东西，不会画出还没做的功能。
