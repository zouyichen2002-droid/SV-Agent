## 3. 建造过程自己暴露的问题

**这一节是这份报告里最有价值的部分。** 二十处问题，
**没有一处能被「跑一遍看输出」抓到** —— 它们全都是「跑通了但结果是错的」。

### 3.1 显示层安静地说了假话（4 处）

| 问题 | 怎么发现的 |
|---|---|
| 仪表盘是快照不是视图，改了歌词页面纹丝不动 | **创作者实测时抓到** |
| 指纹只看 mtime —— 本机 59% 概率两次写时间戳相同 | 修复的测试挂了 |
| 约束清单面板每次渲染现跑复验，破坏了「渲染是纯函数」 | 已有测试挂了 |
| `Session.facts()` 现跑复验，而仪表盘读报告 —— 两个前端看的不是同一个东西 | 库↔CLI 等价性测试挂了 |

最后一条的教训最普适：**一个每次结果都不同的「观察」，本来就不该叫观察。**

### 3.2 两个实现（5 处）

这是本项目最老的病根（`audio.py` 的 0.340 / 0.360）。这轮又抓到五处：

| 重复的东西 | 处理 |
|---|---|
| 对齐计算内联在 `step5_assemble.main()` 里 | 抽成 `align_report()`，抽完数字一模一样 |
| 同轨重叠内联在 `state.inspect` 里 | 抽成 `idem.count_overlaps()` |
| 乐句构造在**四处**各写一遍 | 抽成 `melodize.phrases_of()`，第五份差点写出来 |
| 动作表的幂等列靠动作名**模糊匹配**脚本名 | 改成显式声明 —— 模糊匹配匹配错了也不会报错 |
| 仪表盘与 CLI 各自拼诊断的序列化 | 收进 `session.diagnosis_json()` |

### 3.3 安静地丢东西（4 处）

| 问题 | 不变量 |
|---|---|
| `--restore` 无声冲掉创作者当时的版本 | **任何会丢失当前内容的操作之前，必须先有一张快照** |
| `--adopt` 吞掉「这个文件被外部改过」的信号 | 销毁信号的操作必须如实报告它在销毁什么 |
| 局部重生成把音频轨 · 混音 · 调教全冲了 | `carry_over()` 搬回来；音符变了才丢调教，且**丢得要看得见** |
| `Guard` 缓存账本，两个实例互相盖掉记录 | 真相在文件里，每次现读 |

### 3.4 判据本身有毛病（3 处）

| 问题 | 修正 |
|---|---|
| 第九项检查按**个数**加权，会把已验收的歌判出 4 处问题 | 改按**时长**加权 —— 短经过音是装饰，长音才糊和声 |
| 指标阈值若拍脑袋，会把已验收的歌判成「太平」 | 全部按实测校准，且要求 ≥1.15 倍余量 |
| 「副歌句内极差只有 3 半音」看着很平，其实靠音区抬升 | 三个子指标必须分开报，只看一个会误判 |

### 3.5 模型层（2 处）

| 问题 | 处理 |
|---|---|
| 连续撞限流后报的是「HTTP 429」 | **最常见的失败给了最没用的消息**，改成报上限 · 窗口 · 该怎么办 |
| `gen_lyrics` 给段名加 markdown 粗体，解析器不认 | 在动作里清掉 —— 产出要能直接用 |

### 3.6 我自己犯的两个错，单列

**一、测试文件里写了真 API key。** 想着「要同格式才测得准」，
就把真 key 抄进了 `test_llm.py` 的 `FAKE_KEY`。提交前的密钥体检拦下了。
**测试文件也是要进 git 的文件。** 已确认工作区、暂存区、git 历史三处均为 0。

**二、Bash heredoc 吞反斜杠，这轮踩了 12 次。** 每次表现都一样：
补丁静默失效，或者写出一个语法错误的文件而错误要到下次 import 才暴露。
已记进记忆，规则是「heredoc 里的 Python 字符串一个反斜杠都不要出现」。

## 4. 还缺什么

### 4.1 创作者的验收只走了两项

| 项 | 创作者验过吗 |
|---|---|
| 1 原子写等五件 | **✓ 验过**（红灯 → 拒绝覆盖 → 回滚 → 喊停） |
| 3 会话树 | **✓ 验过**（commit → 否决 → checkout → 改动真的没了） |
| 2 · 4 · 5 · 6 · 7 · 8 · 9 · 10 | ✗ 只有自动判据，可视证据未验 |

自动判据说「机制是对的」，可视证据说「你看得懂」。**后者我替不了。**

### 4.2 端到端还没完整走过一遍

架构文档 §12 的模式 A 判据是「给一句主题，除 FL 三步手动外全程不需要
人手工串脚本」。**这一条还没在一首新歌上完整验过** ——
现有验证都在《晓风残月》这首已完成的歌上做的。

要真正验它，需要开一首新歌，从一句主题走到成品。

### 4.3 明确的能力缺口

| 缺什么 | 现状 |
|---|---|
| 诊断层零实测支撑 | 只启用三条规则，其余一律问。**这是设计，但也意味着大部分诉求它答不了** |
| 「太像上一首」判不了 | 需要参照曲，还没接进去 |
| `adjust_spec` 只有音区偏移 | 调 / 节奏细胞 / 动机在 `SongSpec` 里有，`step3` 没开出开关 |
| `gen_lyrics` 不写文件 | 只产出候选。**这是刻意的**（歌词由创作者拍板），但也意味着还要人工一步 |
| 独特性检查不在 `run_all` 里 | 要外部参照，和「只看这一首」的八项不是一回事 |
| 仪表盘只读 | 点节点回滚需要服务器，第一版所有操作仍在对话里说 |
| 记忆层（L4）基本是空的 | 只有会话树上的否决节点算原料，显式偏好 / 预设都还没建 |

### 4.4 一个悬着的事

**这份 key 早前以明文出现在对话记录里**，而仓库是公开的。
建议去 Mistral 后台轮换一次。

## 5. 建议的下一步

按价值排，不是按难度：

1. **开一首新歌，端到端走一遍。** 这是唯一能验模式 A 的方法，
   而且会暴露一批只在真实使用中才出现的问题 —— 就像第 1 项那次，
   创作者一跑就抓到了仪表盘的假货
2. **补第 2、4–10 项的可视验收。** 每项 2–5 分钟，我可以逐项列出要看什么
3. 记忆层（L4）—— 显式偏好与预设。否决记忆的数据结构已经有了，
   缺的是「把它读回上下文」那一步
4. 「太像上一首」接上参照曲，让诊断层多一条能自动答的规则

**第 1 条最重要。** 十项建造都是在一首已经完成的歌上验的，
而 agent 的真正价值在「从零到一」那一段 —— 那一段还没被走过。
