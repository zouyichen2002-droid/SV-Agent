## 0. 一句话

> 一个**完整体的个人虚拟歌姬创作 Agent**：
> 一句话出歌，也能深度介入修改；正向创作与逆向翻唱共用一套表示、互相校准；
> 出完歌还管作品管理与发布，最终一键出 PV。

## 1. 先把三个目标摊开，它们会打架

你实际上同时要三件事。**它们不是一回事，而且会在具体决策上冲突。**

| 目标 | 成功长什么样 | 什么会拖累它 |
|---|---|---|
| **A. 面试** | 面试官看完说「这人懂怎么造 agent 基础设施」 | 功能堆得多但架构是平的；没有 CI / 可观测性；讲不出失败案例 |
| **B. 产品** | 你真的用它出歌、出 PV、发出去 | 为了架构漂亮过度抽象；一个功能都没做完 |
| **C. 学习** | 你逆向看懂了每一层为什么这么设计 | 我一口气写完两万行，你看不完也讲不清 |

**冲突的具体例子**：

- 「10 亿 token 的工作量」对 B 是好事（功能多），对 A **可能是坏事**——
  面试官看不完两万行，他只会抽查三处。**深度比体量值钱。**
- 「一键发布」对 B 是核心，对 A 几乎不加分（那是 CRUD + OAuth）。
- 「PV 制作」对 B 很炫，但它是**另一个领域**（视频），
  塞进来会让 harness 的边界变模糊——除非它作为「第三个领域插件」出现，
  那样反而是 A 的加分项（证明 harness 真的可复用）。

> **Q1｜当 A 和 B 打架时，优先哪个？**
> 我的建议：**A 优先，但用 B 来验证 A**。
> 即：架构决策按「能不能讲清楚」来定，功能按「能不能证明架构可复用」来选。

## 2. 现在手上有什么（诚实盘点）

推翻之前得知道推翻的是什么。**30871 行 / 146 文件 / 350 条测试。**

### 2.1 已经做扎实的（难复制）

| | 是什么 | 为什么难复制 |
|---|---|---|
| 工具层 | 16 个动作，每个带 JSON Schema、参数校验、写后钩子 | 钩子**按文件指纹触发**，不信动作的自述 |
| 执行语义 | 原子写 + 哈希校验 + checkpoint + 会话树（可回退） | blob 去重的快照，HEAD/checkout/裁决 |
| 安全闸 | 写动作两层闸（工具表不给 + 执行前再查） | 昨天用注入的假模型验过真拦得住 |
| 观测面 | 六步状态 / 五盏灯 / 七项指标 / 八项检查 | 5 个前端共用**同一个** Session，不各算各的 |
| 评测 | 4 个评测器 + 留档报告 | 阈值锚在 **909 首真歌**上，不锚自己的作品 |
| 判断力资产 | 13 份 ADR（带证据链）+ 三个真实失效模式 | **这个最值钱，而且买不到** |

那三个失效模式（2026-09-17~18 实测挖出来的）：

1. **库里用 `SystemExit` 做控制流** → 继承 `BaseException`，
   穿过所有 `except Exception` → HTTP 线程直接死、连响应都不发 →
   用户看到「Failed to fetch」，零解释。**每首新歌必中。**
2. **检查算了却不拦** → 一个「0 句歌词」的输入通过了闸，
   把写好的 20 句词冲掉。数字摆在返回值里看着很负责，实际什么都没挡住。
3. **挑候选的代码是死的** → 标准是「跟某首旧歌最不像」，
   而那个模块 import 一直失败 → 实际行为是「取第一个」。
   表现是「加大候选数反而质量更差」。

> 这三个在全新项目里**几个月都长不出来**。它们是面试里最能讲的东西。

### 2.2 正向与逆向：两条线都有，但互相不认识

| | 规模 | 能力 |
|---|---|---|
| **正向创作** | ~2700 行 | 歌词解析、规格展开、旋律生成、和声、修复循环、八项检查、调教、混音 |
| **逆向翻唱** | ~2000 行 | 人声分离、多声部拆分、音高转写、逐字对齐、参考音频、混音分析、4 个评测器 |

**它们当初是两个独立项目**（「线 1 转写」「线 2 创作」），
数据结构不通、评测不共享、校准不互相喂。
**这正是第 3 节要解决的核心问题。**

### 2.3 一片空白的（基建）

九个标准文件**一个都没有**：`pyproject` / CI / 结构化日志 / 追踪 /
lint / 类型检查 / 多模型抽象 / 5xx 重试 / Dockerfile。

后果已经出现过：
- 350 条测试**只在你本机跑**，没有任何外部证据说它们是绿的
- 昨天你撞的 `HTTP 503`，**没有重试兜底**（只对限流退避，不对 5xx）

### 2.4 最大的结构问题

**通用内核和领域逻辑焊在一起。**
`Session` 直接知道「歌」，16 个动作全是唱歌的动作。

面试官看这个会说「**这是个内置了 agent 的音乐应用**」，
不会说「这是个 harness」。

## 3. 五条需求，逐条拆开

### 需求 1｜完整的 agent harness 架构

> 你的原话：对标企业级创作 agent，综合个人 coding agent 的架构，
> 要比 SynthVCopilot 架构感更强。

#### 这句话拆成可验收的东西

「架构感强」不是感觉，是**有没有这些东西，以及它们是不是真的在跑**：

| 层 | 要有什么 | 现状 |
|---|---|---|
| **能力注册** | 工具/技能的声明式注册，带 Schema、权限、副作用标注 | ✓ 有，但**绑死了领域** |
| **执行语义** | 幂等、重试、超时、预算、可中断、回滚 | ✓ 大部分有，缺重试/熔断 |
| **权限与沙箱** | 谁能调什么、写操作要不要批准、越权怎么拦 | ✓ 有两层闸 |
| **状态与记忆** | 会话状态、长期记忆、检查点、分支 | ✓ 会话树有；**长期记忆没有** |
| **可观测性** | run_id / trace / 结构化日志 / 成本与 token 归集 | ✗ **完全没有** |
| **评测门禁** | eval 跑在 CI 里，退步就挡住合并 | ⚠ eval 有，不挡任何东西 |
| **多提供方** | 换模型不改业务代码 | ✗ 写死 Mistral |
| **人机交接面** | 什么时候必须问人、怎么呈现待决策项 | ✓ 有（五盏灯/六步/确认闸） |
| **可复用性证明** | 同一个内核跑**两个以上**不同领域 | ✗ 只有一个领域 |

**最后一行是关键。** 一个 harness 凭什么叫 harness？
因为**换个领域它还能用**。现在证明不了。

#### 怎么证明可复用

v2 要有**至少两个领域插件**跑在同一个内核上：

```
        通用 harness 内核（领域无关）
     ┌─────────────┼─────────────┐
     │             │             │
  创作领域      翻唱领域      PV 领域
  （正向）      （逆向）      （第 4 条需求）
```

三个领域用**同一套**注册、执行、权限、回滚、观测、评测。
这就是「架构感」的硬证据——不是文档里画的图，是代码里真的复用了。

> **Q2｜「比 SynthVCopilot 架构感强」的验收标准，用哪一条？**
> 我的建议：**「同一个内核跑三个领域」** 作为唯一硬标准。
> 其余（日志、CI、追踪）是及格线，不是亮点。

### 需求 2｜正向创作与逆向翻唱互相学习

> 你的原话：融合正向创作和逆向翻唱，而且可以互相学习。

**这是五条里最有价值、也最容易写成口号的一条。** 得先定义清楚。

#### 「互相学习」不是一个算法，是两样东西

**第一样：一个共享的曲目表示。**

两个方向其实在处理同一种东西——一首歌。但现在：

```
正向：歌词文件 → 内部音符结构 → .svp 工程
逆向：音频 → 音高曲线 → 逐字对齐 → .svp 工程
                     ↑
        两边的中间产物长得完全不一样，互相读不懂
```

v2 要有一个**统一的曲目对象**：段落、句、字、音符、和弦、时间、置信度。
正向「生成」它，逆向「还原」它，两边读写同一个东西。

**这一步做完，「互相学习」就不需要额外算法了**，它变成数据流动。

**第二样：一个双向的校准回路。**

| 方向 | 具体是什么 | 现在有吗 |
|---|---|---|
| **逆向 → 正向** | 你翻唱过的每一首真歌，自动成为生成器的校准样本（音区、句长、和弦贴合、末音长度…） | ⚠ 有静态版：909 首 POP909。**缺的是「翻唱一首就多一个样本」** |
| **正向 → 逆向** | 生成器懂曲式和和声，可以用来纠正转写错误（比如某个音高识别成了不在和弦里的音） | ✗ 完全没有 |

第二条尤其值钱：**转写最难的部分是歧义**，而作曲知识正好是消歧的先验。
这是一个真实的、能讲清楚的技术贡献。

> **Q3｜「互相学习」这一条，是要做成「自动持续校准」还是「手动触发一次」？**
> 我的建议：**先做手动触发**（你翻唱完一首，点一下「拿它校准」），
> 自动化放到后面。自动的东西出错时你看不见，而这个回路一错，
> 全部作品的判据都跟着错。

### 需求 3｜一句话出歌，也能自己参与修改

> 你的原话：用户可以一句话出歌，也可以自己参与修改。

这条**已经基本做到了**（昨天实测：从聊天框一路到 FL 工程）。
v2 要补的是三个洞：

| 洞 | 现在的表现 | 要改成 |
|---|---|---|
| 跨轮对话断片 | 出了 3 版歌词候选，你回一句「选 A」——**它不知道 A 是什么**（候选没落盘） | 候选、方案、分支都有 ID，能跨轮引用 |
| 模型写的词质量不行 | 字数 10–14 不齐、韵脚不押，导致生成器一个候选都出不来 | 约束进提示 + 写入前的硬闸（已有）+ 可迭代重写 |
| 改动粒度粗 | 能改「整首」「某几段」，不能改「第 14 句的末字」 | 更细的定位与局部重生成 |

> **Q4｜「自己参与修改」的最细粒度到哪？**
> 选项：段落 → 句 → 字 → 音符/参数曲线。
> 我的建议：**做到「句」**，字和音符级留给你在 SynthV 里直接改
> （那里的交互本来就比任何界面强）。

### 需求 4｜完全体：作品管理、一键发布、PV 制作

> 你的原话：真的能够一键出一个虚拟歌姬歌曲 PV。

这条实际上是**三个独立的子系统**，难度和风险差得很远：

| 子系统 | 难度 | 风险 | 说明 |
|---|---|---|---|
| **作品管理** | 低 | 低 | 曲库、版本、素材、元数据、检索。工程上是 CRUD |
| **一键发布** | 中 | **高** | 平台 API、鉴权、元数据规范、**版权** |
| **PV 制作** | 高 | 中 | 分镜、素材生成、时间轴对齐、渲染。**是另一个领域** |

#### 关于「一键发布」，有一件必须先说清楚的事

**翻唱涉及别人的作品。** 一键发布 = 把内容推到公开平台。
两者叠在一起，版权风险是实的，不是理论上的：

- 翻唱的词曲著作权属于原作者，多数平台要求授权或走许可通道
- 你自己创作的歌不存在这个问题
- **AI 参与程度需要如实披露**（你之前定的规矩，也是多数平台的要求）

我不会做一个「绕过平台审核」的东西。但**做一个「发布前把该披露的都准备好」的助手**是完全正当的，而且更有用：
它替你整理 AI 参与说明、原作信息、授权状态，然后**你自己按发布**。

> **Q5｜一键发布的边界：是「一键推送到平台」还是「一键准备好发布包 + 你自己按最后一下」？**
> 我的建议：**后者**。理由：① 版权与合规是你的责任，工具不该替你承担；
> ② 对面试而言，「知道哪些动作必须留给人」本身就是加分项。

> **Q6｜PV 是 v2 范围内，还是 v2 之后？**
> 我的建议：**架构上留出位置（作为第三个领域插件），实现放到 v2 之后**。
> 理由：它能证明 harness 可复用（对目标 A 有用），
> 但真做完要吃掉大半工作量（对目标 A 几乎不加分）。

---

### 需求 5｜10 亿 token 的工作量

我理解这是「这是个大工程，别给我做个玩具」的意思，不是一个技术指标。

**但要提醒一句**：体量本身不是目标，而且对面试**可能是负分**。
面试官抽查三处，看的是这三处有多扎实。

> **Q7｜工作量的表达方式，换成什么？**
> 我的建议：换成**里程碑**（见第 6 节），
> 每个里程碑有可验证的产出。体量自然会到，但驱动力是「能不能验收」。

## 4. 对标：上游有什么，我们强在哪

基于 2026-09-16 对 SynthVCopilot 六个仓库的实测调研。

### 他们已经实现的

| 组件 | 能力 |
|---|---|
| `synthv-agent-bridge` | 驱动 SynthV 的桥，67★，仍在更新，9 月新增翻唱曲谱支持 |
| `pi-audio probe` | 单曲特征指纹：BPM / 调性 / 打击比 / 能量弧 / 音区分布 |
| `pi-audio pair-diff` | 有词/无词配对差分 → 单音人声 MIDI |
| FFmpeg 组件 | 受管生命周期 + 固定用途的音频准备 |
| CVRS | 跨版本 `.svp` 参考音频助手 |
| `synthv-toolbox` | Electron 桌面壳、组件安装、插件授权 |

### 他们**没有**的（其 README 自承）

本地 Whisper、源分离、完整 Sound-to-MIDI、歌词对齐。

### 我们的差异化（也就是「架构感更强」具体强在哪）

| 维度 | 他们 | 我们（v2 目标） |
|---|---|---|
| **工具返回值** | 成功 / 失败 | **带度量的结果**：改了几个音符、finding 前后、指标变化 |
| **执行语义** | 无 | 原子写 / 哈希校验 / checkpoint / 可回退 / 预算 / 可中断 |
| **判据来源** | 无量化门槛 | **锚在 909 首真歌**的分布上，不锚自己的作品 |
| **方向** | 正在转向翻唱 | **双向 + 互相校准** |
| **人机边界** | 未显式建模 | 六步状态 / 五盏灯 / 写动作确认闸 |
| **可复用性** | 单领域 | **一个内核跑三个领域** |

**注意一处**：他们的桌面壳、插件授权、多宿主兼容，解决的是
「**分发给第三方**」的问题。你是单用户单工作流，**不建议对标那部分**——
引进来就是为架构而架构。

> **Q8｜要不要做「可分发给第三方」？**
> 我的建议：**不做，但架构上不排斥**。
> 也就是：接口设计得干净，但不投入做安装器、授权、多宿主兼容。

## 5. 架构分层（给你看的版本）

```
┌──────────────────────────────────────────────────────┐
│  交互层    聊天 / 桌面程序 / 命令行 / 仪表盘          │
│           （都只是前端，共用下面同一个会话对象）        │
├──────────────────────────────────────────────────────┤
│  编排层    模型驱动的循环：读状态 → 调工具 → 看数字    │
│           → 决定下一步 / 交回给你                      │
├──────────────────────────────────────────────────────┤
│  内核      能力注册 · 权限 · 执行语义 · 检查点 · 回滚  │
│  （领域    预算 · 可观测性 · 评测门禁 · 多提供方        │
│   无关）   ★ 这一层不认识「歌」这个词                  │
├──────────────────────────────────────────────────────┤
│  领域层    ┌──────────┬──────────┬──────────┐        │
│           │ 创作     │ 翻唱     │ PV       │        │
│           │（正向）  │（逆向）  │（后续）  │        │
│           └────┬─────┴────┬─────┴──────────┘        │
│                └──── 共享曲目表示 ────┘               │
├──────────────────────────────────────────────────────┤
│  外部      SynthV · FL Studio · 模型 API · 音频工具   │
│           （每一个都有「它做不到什么」的显式声明）      │
└──────────────────────────────────────────────────────┘
```

**读法**：

- **内核不认识「歌」** —— 这是整个架构的支点。
  内核只知道「有一个任务、有一些能力、有状态、有检查点」。
- **三个领域共享一个曲目表示** —— 这是「互相学习」的载体。
- **外部依赖都要声明能力缺口** —— 比如「FL 有没有命令行渲染，至今未确认」
  这种事，要写成机器可读的声明，而不是埋在文档里。

## 6. 分期建议

| 期 | 目标 | 可验收的产出 | 对哪个目标有用 |
|---|---|---|---|
| **M0** | 内核与领域分家 | 内核里搜不到「歌/旋律/歌词」任何一个词；现有 350 条测试全绿 | A |
| **M1** | 基建补齐 | CI 跑通、结构化日志带 run_id、多提供方可切换、5xx 有重试 | A |
| **M2** | 共享曲目表示 | 正向生成的歌和逆向转写的歌，**能被同一套检查跑** | A + B |
| **M3** | 双向校准回路 | 翻唱一首 → 它的分布进入校准库 → 生成器阈值跟着动，全程有留档 | A + B |
| **M4** | 交互补洞 | 跨轮引用「选 A」能用；句级修改；模型写词能过闸 | B |
| **M5** | 作品管理 | 曲库、版本、素材、检索 | B |
| **M6** | 发布准备 | 发布包 + AI 参与披露 + 原作信息整理（**最后一下你自己按**） | B |
| **M7** | PV（可选） | 作为第三个领域插件接入，证明内核可复用 | A + B |

> **Q9｜M0 之后要不要先停下来，让你逆向看一遍再继续？**
